# 家具爆品雷达

基于卖家精灵数据，自动监控亚马逊美国站家具市场，发现增长商品、持续热销商品和可参考的开发方向，生成加密报告并推送到钉钉群。

默认监控板材、实木、铁木为主的柜类、桌类、床架、置物架等；剔除沙发、床垫、椅子、软包、布艺抽屉、塑料及配件等不符合范围的商品。

**默认两周一期，卖家精灵调用上限每月 2,000 次。** 系统每天北京时间 08:17 检查，距上次成功运行满 14 天才采集新一期数据。具体范围、阈值和预算以 [config.yaml](config.yaml) 为准，逐条判定说明见 [判定规则说明.docx](判定规则说明.docx)。

## 报告看什么

| 内容 | 主要依据与用途 |
|---|---|
| 突然爆火 | 近 7 或 14 天销量、BSR 明显改善，且通过增长形态、断货、大盘和回落检查；区分新品爆发、老链接重新起量、稳在高位和仍在上涨 |
| 潜力产品 | 上架 30～180 天、评论较少，近 28 天及近 7 天均保持增长；有足够完整月份时验证月度增长 |
| 持续热销 | 最近 4 个自然月中至少 3 个月达到子类目销量门槛，并检查销量规模、波动、月趋势和近期销量；符合条件的头部商品可用月度名单补判 |
| 上升中 | 尚未归入爆火或潜力，但近 28 天及近 7 天均达到增长要求，且没有回落、断货恢复等排除情形 |
| 外观与工艺依据 | 从增长商品提取主材质、风格、造型、工艺、颜色和功能卖点，对比头部或持续热销商品，区分明显更多、常见及也有的特征 |
| 开发方向 | 按增量销售额排列符合条件的子类目，提供产品画像、价格、包装、FBA 配送费和不同品牌的参考商品；没有画像时说明原因 |
| 异常信号与上期对比 | 异常分 ≥3 的商品列出评论、评分、销量等依据供人工复核；空榜表示已有证据未达入榜线。另列商品本期进入、继续上榜或退出的情况 |

增长商品 = 突然爆火 + 潜力 + 上升中。爆火、潜力和开发方向优先按估算的月增量排序；异常信号用于提示核查，不能直接认定刷单。

## 1. 如何理解规则和报告

本说明按当前代码与 `config.yaml` 的默认配置编写，核对基线为代码提交 `d7a4f30`，更新日期为 2026-11-02。修改配置后，以实际运行参数为准。这里的阈值是项目为控制小基数、短促和数据噪声设置的业务筛选条件，不代表行业统一标准，也不是已经证明最优的参数。

报告回答三类问题：哪些商品正在增长，哪些商品长期稳定，哪些增长特征值得进一步开发验证。销量来自卖家精灵估算；分类、金额和开发画像均依赖当期覆盖与证据，不能理解为全市场穷尽结果。

### 主标签与增长样本

每个商品按以下顺序取得一个主标签，前面的优先：**评分偏低 → 异常信号 → 突然爆火 → 潜力 → 持续热销 → 观察**。例如，一个商品同时达到爆火和异常条件，主标签是异常，不进入正向选品样本；评分偏低又优先于异常主标签，因此异常板块也不是全部风险商品的完整清单。

“上升中”是附加判断，只统计没有归入爆火或潜力的观察、持续热销商品。增长商品合计为“突然爆火 + 潜力 + 上升中”，不重复计算。后续外观分析和开发方向使用这批增长商品，并排除异常及低评分商品。

### 阅读顺序

先看数据说明中的覆盖、截止日期和修订提示，再看开发方向及其参考商品，最后逐项核对增长证据、评分、异常分和成本。某板块为空，表示本期已覆盖证据没有达到该板块的门槛；不能直接推断市场上不存在对应商品。

实现位置：[分类与排序](radar/analyze.py)、[业务阈值](config.yaml)。

## 2. 监控范围、发现和追踪顺序

### 类目与商品范围

默认美国站，监控家具、办公家具两个根类目中板材、实木、铁木为主的柜类、桌类、床架、置物架等。子类目末级英文名必须命中保留词且不命中剔除词；默认商品数不足 800 的子类目不单独追踪，最多 30 个子类目，发现时按销售额向下查看两页。

标题再排除软包、布艺抽屉、塑料等商品。皮革、丝绒等面料词需要同时匹配床、床头板、长凳等软包品类才剔除，避免把皮面柜子一并去掉。配件词还检查与家具名词的先后位置：桌面增高架可排除，“带显示器架的电脑桌”仍按桌子保留。范围由正则表达式指定，不能保证所有含糊标题都能正确识别。

### 先发现候选，再拉日数据

月度头部名单每个子类目默认取销售额前 50，并配合按件数的历史名单建立热销依据。新品发现侧重销量最大的 12 个子类目，每个最多 30 个、月销售额至少 2 万美元。名单按父体去重，避免同一款多个变体占满名额。

增长机会主要来自全市场近 30 天名单：**销量至少 300 件，或者销售额至少 4 万美元**，二者满足其一即可。它是采集入口，不能写成爆火或潜力本身的最终门槛。量不足、刚开始起量或不在监控范围的商品，可能尚未进入日数据追踪。

### 初筛的“任一满足”关系

有约 28 天前的自存快照后，候选满足以下任一条件便可争取日数据名额：近 30 天销量相比基准增长至少 15%；半年内上架且相比基准没有下跌；近 14 天两份快照折算的日均达到短期基准的 1.3 倍。无基准的新进名单也保留为候选，不能当作已证实从零增长。

启动期缺少合适自存快照时，使用上月月度名单或约 21～52 天前的其他快照，按基准年龄设增长门槛：不超过 23 天为 10%，不超过 36 天为 15%，不超过 52 天为 10%。基准来自月度名单时，名单自带近 7 天 BSR 改善至少 20% 也能触发初筛。月销量先按月份天数统一口径，换代表子体时按父体匹配。

### 预算不足时先看谁

优先安排上一期爆火、潜力、异常商品，默认最多 300 个；另留头部名额 30 个，优先各子类目月销量第一。之后按初筛优先级补机会候选，追踪池上限 3,000，同时受本期剩余调用预算约束。

新进名单中近 7 天 BSR 改善至少 20% 的优先；其他候选综合基准增长和短期持续性排序，避免只凭一个极高增长率占用名额。基准名单没翻全的子类目会单独标明，不能据此证明商品此前没有销量。默认关闭根类目增长榜、相似款扩散和低量新品补捞，避免重复占用预算。

### 月度名单尚未更新完

同子类目相邻两个月有销量的共同商品至少 5 个，其中至少 50% 月销量完全相同，视为上月名单可能尚未更新完，后续只重拉受影响子类目。报告注明该状态；它是数据成熟度提示，不能解释成真实销量完全没变。

实现位置：[范围与发现](radar/discovery.py)、[全市场初筛与大盘](radar/universe.py)、[追踪池](radar/tracking.py)、[历史名单](radar/monthly_lists.py)；参数为 `scope.*`、`discovery.*`、`pool.*`。

## 3. 所有板块共用的数据边界

### 评分和数据时效

默认评分至少 4.0；已知评论数不足 100 条时，最低评分提高到 4.2。没有评分的商品不直接判为低评分；评论数未知时使用一般评分线，不能自动当作零评论。优先使用日数据的最新评分，缺失时才回退名单信息。

日数据相对“本批最新数据日”和“本期判定日期”中更晚的日期，落后超过 2 天时，不判爆火、潜力或上升中；整批都停更则中止新报告发布。超过 2 天才排除，恰好 2 天仍在允许范围内。重生成历史报告使用原报告日期，不把今天的时间直接套到过去。

发布还要求实际刷新日数据达到本期计划的至少 60%，并且至少成功刷新 1 个。核心采集失败、额度在核心阶段耗尽或刷新比例不足时，不用残缺结果发布新一期；已取数据和调用记录保存，供后续接续。

### 缺失、明确为零和对比期较短

缺字段、没有覆盖到的日期、缺少基准，均保留为未知。只有明确记到的零销量才是零，不能用空窗口代替。若过滤后仍有在卖观察，按其真实均值计算；若因断货过滤后没有在卖观察，要补认零基准，则至少需要 7 个明确零值且其他非大促有效销量也都是零。

爆火、潜力、上升中的基准会剔除 BSR 缺失或 BSR 至少 1,000,000 的日子；潜力、上升中还剔除连续至少 3 天明确零销量的断货段。大促日不会把连续零销量段拆开。当前期日均保留当前真实低量或零量，避免把近期下滑也从分母中删掉。

对比期在卖天数不足 14 天会标注具体天数，一般不单凭这一点禁止增长分类；但老链接和老品换链接的增量会采用更保守处理，详见第 12 节。评论增速需要的销量分母更严格：区间每天都必须有有效、非负且有限的销量，缺一天就不能计算该项。

### 自然月与日均口径

热销及潜力的月度趋势只用数据截止日前已经结束的自然月，未来月份不参与。最近 4 个月就是连续的 4 个日历月，不能缺一个月就拿更早月份补位；月趋势保留真实月份间隔。月环比对 `ln(月销量 + 1)` 按月份位置作线性拟合，再以 `exp(斜率) - 1` 换算每月增长率；零销量可以参与，有效月份不足 2 个时无法估计。第 8 节的新品累计销量是另一口径，需要覆盖截至当期月份。

日均使用窗口内已知有效观察，按具体规则排除大促或断货日，并非所有指标都要求窗口每天齐全。报告有缺数提示时应同时看样本长度，不能把一般日均与要求完整区间的评论比混为一谈。

### 大促、市场整体增长与销量修订

大促自动识别使用商品前 14 天销量中位数，至少 70% 日期有数据，且基准日销至少 3 件；当天至少 40 个合格商品参与，达到自己基准 1.8 倍的商品占比至少 30%，才认作核心大促日。相邻日冲高占比至少 15% 可延伸；配置登记的活动也要有至少 15% 的数据印证。日度增长比较跳过确认的大促日，不做季节性调整。

品类大盘用同子类目共同商品的销量倍数中位数，至少 10 个有效商品，将比较跨度统一折成 28 天，最高按 2 倍处理。大盘大于 1 时，爆火、潜力、上升中的销量增长倍数先除以大盘，再比较各自门槛；从零起量没有普通增长倍数，不做这一步。大盘不足 1 不会反向放宽门槛。

默认修订模式为 `correct`。历史修订测量需要至少 30 个日期对齐的有效共同商品，并达到至少 2% 的变化幅度；只有测到历史下调、且当前近期偏高证据足够时才校正最近对应窗口。当前偏高确认线为 `1 + (1 / 历史修订中位数 - 1) × 0.5`。例如历史通常乘 0.8，当前偏高线是 1.125；不能无条件把全部销量乘 0.8。样本或当前偏高证据不足时保留原口径并提示敏感性；`tag` 模式只提示，不改金额及排序。

实现位置：[日序列与窗口](radar/series.py)、[大促](radar/detect/events.py)、[销量修订测量](radar/tracking.py)、[综合判定](radar/analyze.py)；参数为 `thresholds.stale_days`、评分项、断货项、`events`、`tide` 和修订项。

## 4. 突然爆火

### 普通增长必须同时满足什么

分别比较“近 7 天与此前 28 天”和“近 14 天与此前 28 天”。**每个窗口独立走完量、BSR、形态、断货恢复、大盘等条件；任一窗口全部合格即可**，之后选合格窗口中强度最高的。不能先挑一个销量倍数最大的窗口，再用它的失败结论覆盖另一个合格窗口。

| 检查项 | 默认条件 | 设置目的 |
|---|---|---|
| 绝对量 | 近期日均至少 3 件 | 减少极小基数波动 |
| 销量倍数 | 近期日均 / 基准日均至少 2.0 | 要求有明显放量 |
| BSR 改善 | 近期 BSR 中位数 / 基准中位数不超过 0.5 | 用排名共同确认增长 |
| 跑赢大盘 | 大盘上涨时，销量倍数 / 大盘仍至少 2.0 | 减少随市场普涨入榜 |
| 持续性 | 通过下述形态，且没有回落 | 排除尖峰和已经结束的增长 |

近期价格中位数比基准下降至少 15%，只标注“降价驱动”，不单独取消爆火；开发时应自行评估能否承受同样价格。

### 从零起量的特殊条件

基准已知且日均低于 0.5 件时，按从零起量处理，不计算普通翻倍。缺少可用旧 BSR 时可以不要求排名翻倍；若有旧 BSR，仍检查改善。近期日均必须达到 **30 件与“子类目第 20 名月销量 / 30 × 25%”中的较高值**，并通过形态、脉冲和回落检查。

上架不超过 180 天称“新品爆发”；超过 180 天或上架时间未知称“老链接重新起量”，不能当作新品。低于确认量的只作为起量提示；老品换链接不按从零新品爆发认定。

### 什么形态才算持续

形态取最近 7 个非大促观察日，最多往前查 14 个日历日，按以下顺序判断：先排脉冲，再识别从零起量，再判断稳在高位或仍在上涨。

- **短时脉冲**：最近 7 个观察日的正增量中，最大的 2 天合计至少占 60%，取消爆火，包括从零起量。
- **稳在高位**：至少 5 天销量达到基准的 1.5 倍，且最近 3 天日均与这 7 天日均的比值在 0.85～1.15。
- **仍在上涨**：最近 7 天日均至少为再之前 7 天的 1.15 倍，且最近 3 天日均高于最近 7 天日均。
- 其余为形态不稳，不仅凭销量和 BSR 翻倍入榜。明确断货恢复、数据过期、正在回落、评分偏低或异常主标签也不入爆火板块。

### 排序与例子

板块先按第 12 节的月增量销售额降序，同额看爆发强度。窗口选择强度为 `min(销量倍数, 10) × log(1 + 近期日均)`，从零窗口无普通倍数时内部用 5 计算；这不是板块主排序，也不是销量预测。

例如，销量达到 2.4 倍而大盘为 1.3 倍，扣大盘后约 1.85 倍，普通爆火不成立；即便销量和 BSR均达标，若只有两天尖峰贡献大部分增量，仍不能入榜。

实现位置：[爆火、断货与形态](radar/detect/rules.py)、[逐窗口业务过滤](radar/analyze.py)、[形态计算](radar/series.py)；参数为 `thresholds.surge.*`。

## 5. 潜力与上升中

### 潜力产品：同时满足

1. 已知上架时间，年龄在 30～180 天，包含两个端点；已知评论数必须少于 300，恰好 300 不符合。评论数缺失不会自动等同于评论很多，仍按其他条件判断。
2. 近 28 天日均至少 2 件，且至少为再之前 28 天在卖日均的 1.2 倍；基准必须能支持有效的正销量倍数，未知或零基准不靠无限倍数过关。
3. 最近 7 个非大促观察日的日均，相对同一旧 28 天基准也至少 1.2 倍；大盘上涨时，两项倍数均先除以大盘。
4. 最近 3 个已结束自然月中、上架月之后有至少两个可用月份时，月销量对数趋势换算的月增长率至少 15%；月份不足则注明“月度增长尚未验证”，不冒充已经验证，也不单独据此否决。
5. 不属于老品换链接、断货恢复、脉冲抬高、回落、过期、异常或低评分商品。

设置 30 天下限，是给新品留下观察积累；半年、评论少于 300 用来控制成熟度；28 天和最近 7 天同时增长，用来避免前半月上涨但已经走平的小品被保留。板块按月增量降序，同额看增长。

### 上升中：补充仍在增长的商品

没有进入爆火或潜力的观察、持续热销商品，近 28 天日均至少 3 件，且近 28 天与最近 7 个非大促观察日相对旧 28 天在卖基准均至少 **1.3 倍**；大盘上涨时扣除大盘后仍要达标。它不要求半年内上架或少于 300 条评论，适合捕捉老款稳定增长。

同样排除断货恢复、短时脉冲、回落、过期、低评分和异常。持续热销可同时带“上升中”标签；爆火、潜力不再重复记一次上升中。

### 容易误读的例子

近 28 天比旧基准增长 50%，但最近一周已回到基准的 1.05 倍，则潜力和上升中都不成立。一个商品因评论超过 300 不够潜力，仍可能符合爆火或上升中，不等于被整体排除。

实现位置：[潜力](radar/detect/rules.py)、[最近一周持续性与上升中](radar/analyze.py)；参数为 `thresholds.potential.*`、`thresholds.rising.*`。

## 6. 持续热销与只有月度数据的补判

### 子类目门槛怎么确定

将同子类目的销售额头部名单与按件数头部名单合并，按父体去重，再按月销量排列，取第 20 名的月销量作门槛；不足 20 个时取已有样本最后一名，完全没有有效样本才无法设门槛。它是当前可用头部样本的相对门槛，并非对每个历史月重新查询一遍真实全市场第 20 名，小样本时尤其需要结合绝对量门槛阅读。

### 日数据商品的条件

- 最近 4 个已结束的日历月，至少 3 个月月销量达到子类目门槛；每个计入的月份还要满足销量至少 150 件或销售额至少 2 万美元。
- 最近 6 个日历月中已知月销量的变异系数 CV 不超过 0.35。CV 是标准差 / 均值，衡量稳定度；不是要求 6 个月都必须有值，缺月仍保留缺口。
- 最近 3 个已结束月份可计算趋势时，每月趋势不低于 -15%；趋势不可计算不单独否决，但仍必须满足其他条件。
- 最近 28 天日均至少达到前述 6 个月已知月份平均日均的 70%，必须有近期证据，不能只凭历史成绩。

这些条件用于同时控制规模、稳定和近期有效性。持续热销可以出现短期回落，此时保留热销标签并提示“最近回落”；它不一定正在增长。板块按 6 个月已知月销量均值降序。

### 没拉日数据时如何补判

尚未日数据追踪的商品，在对应子类目最近连续 6 个月均出现在销售额前 50 或销量前 50 的名单中，才进入月度补判。近 30 天名单必须有当期有效销量，除以 30 得到近期日均，按确认的大促影响及实际启用的修订校正统一口径后，再走热销条件。不能拿缺失近期销量当作历史水平仍然有效。

与已经追踪商品同父体的代表子体不会重复补判。只有月度数据时，不画日走势图、不判断日度回落，不计入“已追踪日数据商品数”。

月度补判也检查留评率和有效评论核查。异常分达到入榜线时，归“异常信号”，附“长期头部”，不再计入持续热销数量，不能认为长期大卖天然没有异常。

实现位置：[热销判定](radar/detect/rules.py)、[月度补判](radar/analyze.py)、[名单补齐](radar/monthly_lists.py)；参数为 `thresholds.hot.*`。

## 7. 回落、恢复和老品换链接

### 回落：以下任一成立

| 情形 | 默认判断 |
|---|---|
| 冲高后继续下降 | 最近 3 天日均低于近 28 天最高连续 3 天日均的 75%，且低于再之前 3 天日均的 90% |
| 整周走低 | 最近 7 天销量中位数低于再之前 7 天中位数的 85% |
| 峰值后连续下滑 | 近 7 天峰值后至少连续 3 天没有回升，最后一天不超过峰值的 70% |

任一成立就撤销爆火、潜力、上升中，持续热销可保留并提示。这里描述的是近期走势；“不再爆火”只是上期对比分类，两者含义不同。

### 断货恢复：必须有明确证据

爆火对比期中，明确零销量或 BSR 达到断货线的天数至少为“7 天”和“有效对比窗口长度的 25%”中的较高值；再往前 90 天还要有至少 14 个非零销售日，且其日均至少是当前近期日均的一半。满足才认作恢复供货，排除增长板块。

缺数据不能当成断货。没有足够更早销售历史的真正新品，不会单凭旧窗口零销量被判成恢复。恢复到更早高位但不满足上述断货条件时，仍可能有增长标签，但月增量另作保守处理。

### 老品换链接：不是单看上架短、首周卖得多

已知上架不超过 180 天，且累计评论 / 当前 ASIN 已观测累计日销量达到 50%；或者该比例达到 15%，再有以下任一证据：从首个销售日起的一周日均至少 5 件且达到最近 7 天日均的一半；第一次达到该量级后的一周也保持该量级，前一周日均不超过后一周的 10%；有效抽查中的近 60 天评论总量不足按现有评论数推算应有值的一半。

标记后不作为潜力或真新品从零爆发，不用继承评论给新品评论比、月度留评率加分。但它仍可能凭自己的稳在高位、持续上涨或上升中证据入选。基准涉及开卖首周时只标注，不一律封禁；基准短时的月增量按第 12 节处理。

这里的累计销量是可观测的本 ASIN 日数据总和，不等于平台完整终身成交记录。该标签用于提示链接历史可能与上架日期不一致，不能直接确认真实迁移原因。

实现位置：[回落、恢复与换链接](radar/detect/rules.py)、[增量恢复过滤](radar/analyze.py)；参数为 `thresholds.momentum.*`、`thresholds.relist.*` 和恢复相关项。

## 8. 异常信号：计分、去重和不计分

### 入榜和分值含义

总分 **至少 3 分**进入异常信号，**至少 5 分**为更高风险等级。分值是人工复核优先级，不是刷单概率或违规认定。只有标签、只有 1～2 分或没有足够证据，不进入异常板块；评分偏低优先取得主标签，也可能不在该板块出现。

| 信号 | 默认条件 | 分值 |
|---|---|---|
| 月度留评率偏高 | 扣除可用 Vine 影响后，新增评论至少 10 条；留评率至少为 6% 和子类目中位数 3 倍中的较高值 | +2 |
| 新品评论 / 累计销量偏高 | 上架不超过 90 天、累计评论至少 20；扣除 Vine 后自有评论 / 完整累计销量至少 10% | +2；已有留评率分时 +1 |
| 两次观察间评论异常增加 | 扣除 Vine 后新增至少 10 条；完整区间销量明确为零，或评论增量 / 销量至少为 15% 和子类目留评率 3 倍中的较高值 | +2；前两类已计分时 +1 |
| 评分跳升 | 与 45 天内前次有效观察相比，评分提高至少 0.2，累计评论至少 50 条 | +1 |
| 非大促销量脉冲 | 最近 30 天出现 1～3 天冲高，起点至少为前 28 天销量中位数的 3 倍且至少 6 件/天；之后至少间隔 3 天、最多看 7 天，可用日均低于基线 1.3 倍 | +1 |
| 抽查评论集中 | 样本至少 10 条，评论最多的 3 天占比至少 30%，且条数严格高于同样条数和时间跨度下均匀随机分布的 99% 分位 | +2 |
| 非验证购买偏多 | 明确有验证购买标记的样本至少 10 条，其中非验证购买比例至少 50% | +1 |

前三类都在表达“评论相对销量过多”，因此重叠时降权，避免按三个独立实锤叠满分；评分跳升、抽查集中等有独立证据时可另计。异常板块按总分降序，同分按近 28 天日均降序。

当前接口的评论和销量按父体口径比较，不再因变体多而把比例除以变体数；否则同一批父体数据会被重复稀释。父体混用、合并或继承造成的不一致，使用以下独立检查处理。

### 哪些情况不应该加分

月度新增评论超过当前累计评论的 `1.05 倍 + 5`，视为父体口径可能不一致，该留评率不计分。有效核查表明评论主要继承而来、或已标记老品换链接时，对应留评率、新品评论比不计分。

评论增速使用此前 45 天内记录到的最高评论数作基准，找不到才回退前次有效观察，避免“100 → 80 → 95”被当成新增 15 条。完整销量区间缺一天就不计算评论增速比；明确为零才能触发“有评论、无销量”的信号。确认父体或变体合并时，相关评论增速不计分。

新品累计销量优先使用从上架月到数据截止月均完整、非负且有限的月销量，未来月份忽略；月度不齐再查上架日起的完整日销量，仍不齐则标注证据不足，不计算新品评论比。不能把剩余半段历史当作累计销量。

“变体合并”“大促脉冲”“Vine 评论多”是解释标签，本身不加分。Vine 占抽查样本至少 30% 时给提示；有实际有效比例就按比例估算应扣量，没有可用比例且上架不超过 90 天时，对累计前 30 条作可能 Vine 的保守扣减。**30 条是当前项目参数，不是本说明对平台最新政策的断言。**扣减前本来达到异常条件的新品会争取核查名额，避免一直靠猜测排除。

### 抽查为什么还要比较随机分布

少量评论天然容易集中，例如 10 条分别落在 10 天，最大的 3 天也占 30%。因此不能只看 30%：程序按实际样本量和有效跨度作固定种子模拟，需同时超过 99% 分位，减少小样本假异常。该模拟是内部筛选参考，不等同于已经建立统计检验意义上的刷评结论。

### 异常板块为空应该怎么判断

先看本期日数据覆盖、核查数量和证据不足提示，再看是否存在低评分商品或只有 1～2 分的候选。空榜可能是正常未达线，也可能是尚未获得有效评论证据；不能为了让板块“有内容”而降低分数或把未知字段当异常。仍应优先人工复核高销售额、单条信号较强但尚未补查的商品。

实现位置：[异常计分](radar/detect/fakehot.py)、[完整销量区间](radar/series.py)、[核查证据](radar/evidence.py)；参数为 `thresholds.fake.*`。

## 9. 评论和详情核查怎么分配与失效

### 每期名额及优先级

每期最多 15 次核查调用，**评论查询和父体/变体详情查询共用总额**。其中预留 5 次给尚未上榜但已有至少 2 分的候选，不额外增加总预算；候选不足时归还其他核查。

评论数相比前次上涨至少 30%、又缺少新鲜详情核查时，优先检查父体与变体，详情也占这 15 次。其后常规评论核查次序为：可疑的上榜商品；报告与通知点名的商品、开发方向参考候选；未上榜的至少 2 分候选；其余爆火、潜力；因可能 Vine 扣减而暂时未达标的新品。同优先级再结合异常分、增长强度和销售额安排，预留名额仍受保障。预算不足者并不等于通过了核查。

### 评论样本不能冒充全部评论

默认抽查截至商品数据日之前约 60 天的最新评论，查询与返回过滤都使用同一截止边界。接口通常只返回最新一页，记录抽样条数、总量和覆盖跨度。只拿到部分样本时，集中度跨度按样本最早日到截止日估计，至少 7 天；确认完整覆盖时按 60 天比较。非空响应若全部被日期过滤掉，不保存为一条新的有效核查。

验证购买标记只认明确的真/假值；缺失保留未知，至少 10 条有标记才能给非验证购买比例计分。Vine 比例要求该样本的 Vine 标记完整，否则不使用这个比例。0 条样本却声称总量非零或总量未知的异常结果，不作有效证据。旧缓存缺少明确标记样本数的比例也不继续当作可靠比例。

### 时效、身份和历史回放

评论与详情核查按业务日期计算，取得时间距判定日必须是 0～13 天，恰好 14 天失效；评论样本截止日也需仍然新鲜。评论核查绑定当时父体、变体信息：已知父体改变，或者变体数变化达到“2 个”和“旧数量的 30%”中的较高值，就不沿用该评论核查。详情核查保留前后结构，供识别合并使用。数据供应商时间可比业务日期早晚一天，所以“取得日期”和“样本截至日期”分开保存判断。

历史重生成只允许使用当时已经知道的核查，不使用后来查到的评论或父体结构。更新追踪信息前保留旧父体快照；同一天只更新评分也保留，缺失字段不会覆盖同日已有有效值。这些边界直接影响异常加分和继承评论豁免。

实现位置：[核查排队与样本整理](radar/verify.py)、[时效与身份](radar/evidence.py)、[观察记录](radar/tracking.py)；预算为 `budget.review_checks`、`budget.review_checks_unlisted`。

## 10. 外观、工艺、关键词与主材质

### 样本和来源

标题词库提取风格、造型、工艺、颜色、功能卖点；与全部月度头部样本比较。标题共性统计至少要有 3 个增长商品、20 个头部样本，否则不作这组共性总结。主图侧默认选势头较强的 50 个增长商品，与最多 40 个持续热销且不属于增长的商品作对照；开发方向所需的商品也可进入识别候选。没有模型密钥或识别结果时，按可用标题、属性证据展示。

主图是被选样本的观察，不等于已经识别全部市场；标题表示卖点表达，主图表示可见特征，两者来源分别保留。颜色在有主图依据时优先主图，避免标题列举多个可选色造成误判。

### “更多”“常见”“也有”的区别

所有列出的外观特征至少需要 2 个增长商品、2 个已知品牌支持；未知品牌商品可以保留在统计样本，但不能充作独立品牌。

| 分档 | 默认条件 | 允许得出的结论 |
|---|---|---|
| 更多 | 标题占比至少 10%，平滑后相对头部至少 1.3 倍；或主图占比比持续热销对照高至少 10 个百分点 | 在本期可比样本中相对更突出 |
| 常见 | 未进“更多”，增长侧占比至少 30% | 多个增长商品都有，不代表正在变多 |
| 也有 | 未进前两档，增长侧占比至少 10% | 有一定支持，证据弱于常见 |

标题倍数采用 0.5 的平滑计数，避免头部为零直接得到无限倍数。如果有效标题说更多、有效主图却说更少，或相反，视为冲突，三档都不强行列入。两种依据都支持的特征会适当优先；更多按占比差排序，每维默认最多 6 个，常见最多 3 个。

### 其他共性和关键词

价格带、评分、评论等结构化共性，要求至少 2 个增长商品、增长侧占比至少 20%、平滑相对倍数至少 1.5；按倍数与占比综合排序，最多 10 条。价格、评分、评论数另给两侧中位数，缺值不按零加入。

关键词先去品牌和通用词，再看商品级支持数；增长样本至少 20 个时支持至少 3 个，否则至少为 2 与样本量 15% 向上取整中的较高值。平滑倍数至少 2，优先保留有效双词组合，最多 15 个。它们反映标题共现，不证明关键词带来销量。

### 主材质单独统计

每个商品只取一个主材质，优先亚马逊 Material 属性，其次标题明确的具体材质，再取主图识别，最后才使用标题中笼统的木质。分类包括铁木、实木、板材、金属、木质未注明、未注明、其他等；不把“看起来像木纹”直接当实木。

增长商品与持续热销对照组分别统计材质占比，未知类别保留在分母，并注明属性查询覆盖。每期 Material 查询最多 30 次，查过会缓存；未覆盖不等于没有该材质。主材质构成是描述性比较，不自动套外观的“更多”评分。

实现位置：[词库与标题统计](radar/detect/design.py)、[共性及多源合并](radar/detect/traits.py)、[主图识别](radar/vision.py)、[主材质](radar/materials.py)；参数为 `thresholds.appearance.*`、`llm.vision_*`。

## 11. 开发方向与产品画像

### 哪些子类目有资格

同子类目至少 2 个增长商品、至少 2 个已知品牌，才形成候选方向。按该类目增长商品的月增量总额降序；同额依次看品牌数、增长商品数、爆火商品数和势头顺序。默认 `max: 0` 表示全部合格方向都可展示，本期要点与钉钉只摘要前 5 个有画像的方向。

若没有任何共同特征，也没有明确主材质，无法形成可执行画像，该类目跳过画像但仍在全部子类目一览中出现，注明原因。增量很大却没有画像的方向还会单独提示，避免只看摘要漏掉。

### 同子类目头部怎么选

从月度名单取同子类目月销量前 30 个，排除本期增长商品及其同父体商品。头部至少要有 10 个已知品牌，才允许说“比头部更多”。如果识别了主图的头部已有至少 10 个已知品牌，两边都用标题与主图；否则两边都只用标题。不能增长侧看图、头部侧只看标题后直接相减。

头部品牌不足 10 个时，只列共同特征，不声称已与头部比较。此时可使用现有主图辅助描述，但不输出相对优势结论。

### 品牌等权，防止一个大卖家主导结论

外观特征先算一个品牌内部商品的特征占比，再对已知品牌取等权平均，增长侧和头部侧都这样做。例：品牌 A 有 10 个商品、其中 5 个有该特征，品牌 B 有 1 个且具有；品牌均占比是 `(50% + 100%) / 2 = 75%`，不是商品总数口径的 `6 / 11`。

“比头部多”要求至少 2 个品牌支持、品牌均占比高至少 20 个百分点，且至少是头部的 1.5 倍。“基本款”要求品牌均占比至少 50%、至少 2 个品牌支持且没进入更多；没有充分头部时同样门槛称“共同特征”。每个维度每档最多 3 个。

主材质按品牌支持统计：一个品牌任一增长商品是该材质即视为支持；至少半数已知品牌且至少 2 个品牌支持才列。它与外观“品牌内部占比再平均”的计算不同，不直接声称比头部更多。

### 画像还包含什么

价格列本类目增长商品的最低～最高价，有至少 3 个有效价格才列中位数；包装体积、包装重量和 FBA 费用分别对有值商品取中位数。参考商品选本类目势头靠前、异常分为 0 的最多 2 个，要求已知且不同品牌；不足就少列，不能拿未核查当作已证实安全。

全部子类目一览同时列日数据追踪量、增长商品和品牌数、爆火数、月销售额、月增量、大盘与缺画像原因。画像是下一步找工厂、核价格和差异化设计的线索，不是直接立项结论。

实现位置：[开发方向及全类目一览](radar/detect/directions.py)；参数为 `thresholds.directions.*`。

## 12. 金额、增量、包装与费用口径

### 月销售额和月增量

估算月销售额 = 近 28 天日均 × 当前售价 × 30。估算月增量 =（近 28 天日均 − 再之前 28 天在卖日均）× 当前售价 × 30。实际启用修订校正时使用校正后的近期日均，大促日按相应比较口径剔除。两个量都不是已结算自然月财报，也没有把促销、变价和广告利润完整建模。

基准未知显示“无法估算增量”，不计入合计，不能表达成确定零需求；已知从零且证据足够的真新品可以计算。若实际算出负增量，保留其方向，不把所有负值强行改为零。

### 以下情况不计正增量

- 老品换链接，旧 28 天无可用基准或在卖不足 14 天。
- 从零起量但属于老链接重新起量。
- 上架超过 180 天的老链接，旧 28 天在卖不足 14 天。
- 当前水平没有超过旧基准之前 56 天内、在卖至少 14 天的历史连续 28 天最高日均。普通比较看近期 28 天，爆火的恢复检查按选中的 7/14 天窗口另核对。
- 没有售价，无法形成金额。

这些情况金额栏按规则归零并写原因，目的是避免把恢复供货、流量迁移或回到旧水平都解释成新市场需求；不是证明该商品没有商业价值。

### 包装与 FBA 的边界

使用卖家精灵提供的**包装**长宽高、包装重量和 FBA 估算值，不用组装后商品尺寸替代。尺寸统一到英寸，体积为长 × 宽 × 高 / 1,728，单位立方英尺；再乘 0.0283168 转成立方米。重量统一到磅，费用为美元。

每个汇总指标只用自身有值商品，缺尺寸但有重量的仍可参与重量中位数；“有包装数据的商品数”不代表每项费用都完整。FBA 占售价比例对每个有费用与售价的商品先计算，再取中位数，不等于两个中位数相除。

FBA 这里主要是配送费估算，不含佣金、仓储、广告、退货、工厂采购、头程运输等完整成本。报告不直接输出净利润或投产通过结论；实际开发需以报价、包装方案和当期费率核算。

实现位置：[金额与保守归零](radar/analyze.py)、[包装解析与汇总](radar/shipping.py)。

## 13. 上期对比、数据提示与文字简报

### 与上期对比不是未来预测

依旧爆火：上期和本期主标签都为爆火。新进入：本期进入某板块、上期不是该板块，若由其他板块转入则注明。不再爆火：上期爆火，本期仍追踪但只有观察或低评分；不是所有离开爆火的商品都归这一项，转潜力、热销或异常会在对应变化中说明。

此前没追踪的商品，使用当前可得历史日数据回看上期日期，避免把本来已达标的商品说成刚增长；它是回看结果，不能冒充上期实际已经跟踪。新获得月度覆盖而补判热销的商品单列“补判”。没追踪到的不直接说成回落。

上期若提示大促后数据待修订，还会复核上期所有增长商品，本期仍增长、不再成立、未追踪分别列出。历史回看限制日期和已知核查，仍可能受到供应商事后修订历史销量的影响。

### 只提示、不直接取消上榜的数据问题

增长商品变体数比约一个月前增加至少 30% 且至少增加 2 个，提示可能有新变体销量；近 30 天名单与日销量两边均至少 60 件、相差至少 2 倍，提示口径不一致；最近 28 天至少 7 天缺日数据，提示判断可能不稳。这类数据提示与第 3 节的强制过期排除不同。

近期出现广泛 BSR 改善但销量可能尚未修订时也会提示：默认近 10 天内，至少 40 个合格商品、历史 BSR 中位数不超过 300,000，其中至少 10% 的当日 BSR 改善到基准的 1/1.8，连续至少 2 天。该提示不直接改分类。

### 自动文字怎么产生

分类、分数、金额、方向和参考商品由程序先算好；文字模型负责归纳已算结果，不能另定入榜线。未配置文字模型时用模板简报；没有主图识别时按已有非视觉证据展示。阅读简报仍应回到商品证据与数据说明核实，不能把文字表述当作额外证据。

实现位置：[上期对比](radar/detect/diff.py)、[历史回看与数据标签](radar/analyze.py)、[报告](radar/report/render.py)、[文字简报](radar/narrative.py)。

## 14. 参数怎么调，规则怎么维护

### 先调覆盖，再考虑放宽判断

未看到某个商品，先核对类目和标题范围、全市场量门槛、当期预算是否取得日数据，再核对评分、时效、基准、脉冲、大盘、回落与异常证据。只有漏掉的商品已经覆盖且存在稳定误判样本，才考虑修改对应判断边界，不因一个板块为空就整体放宽。

### 参数分组与影响

| 参数组 | 控制内容 | 调整时应观察 |
|---|---|---|
| `scope`、`discovery`、`pool` | 看哪些类目、候选和商品 | 调用数量、低量噪声与漏覆盖 |
| 评分、时效、断货、修订项 | 哪些数据适合用于决策 | 有效样本、未知值和边界说明 |
| `surge`、`potential`、`rising` | 增长幅度与持续性 | 短促误入、成熟款被漏掉、最近一周是否保持 |
| `hot` | 长期规模与稳定 | 相对门槛、缺月、近期证据 |
| `fake` 与核查预算 | 异常证据强度与核查覆盖 | 小样本、证据重叠和未核查候选 |
| `appearance`、`directions` | 特征与画像支持度 | 品牌数、对照一致性和样本偏差 |

默认每月调用上限 2,000，按本月剩余期数均分；间隔 14 天，本期最多 2,500 次。Material 查询最多 30、往月名单补齐最多 50、评论与详情核查共 15 次。额度会限制覆盖，增加核查或补齐量可能挤占日数据名额，需要同时评估。

### 修改规则后的核对要求

同步修改实际配置、计算逻辑、报告板块说明、README 和本 Word 说明。验证恰好达线、刚低于线、缺失、明确零、缺月、过期、父体变化等边界；必要时用同一批真实保存数据回放比较，说明哪些商品被加入或移出，不能只展示新增数量。

本说明不承诺“没有任何漏洞”。规则已覆盖主要增长、稳定度、异常和数据边界，仍受销量估算、标题范围、样本选择、接口字段与预算约束。后续以能复现、影响选品结论的实际问题为依据修正，避免为了增加功能而堆叠规则。

实现位置：[全部默认配置](config.yaml)、[自动测试](tests/)。


## 本地试用（Windows）

使用 Python 3.11，在仓库目录打开 PowerShell：

```powershell
python -m pip install -r requirements.txt
python -m radar demo
```

演示使用模拟数据，不调用卖家精灵或钉钉；用浏览器打开生成的 `out/demo/report.html` 即可预览。

真实运行前，将 [.env.example](.env.example) 复制为 `.env` 并填写所需密钥；已有 `.env` 时直接编辑。随后执行 `python -m radar run`。本地数据保存在 `site/`，与 GitHub 的 `site` 分支相互独立。

### 密钥配置

本地写入 `.env`；线上写入仓库 **Settings → Secrets and variables → Actions → Secrets**。

| 名称 | 用途与获取方式 |
|---|---|
| `SELLERSPRITE_SECRET_KEY` | 真实采集必填，在 [卖家精灵开放平台](https://open.sellersprite.com) 获取 |
| `REPORT_KEY` | 数据和报告加密必填；安装依赖后运行 `python -m radar keygen` 生成，**务必另行备份** |
| `DINGTALK_WEBHOOK`、`DINGTALK_SECRET` | 推送钉钉时填写；在群内添加自定义机器人，安全设置选择“加签”，保存 Webhook 和 SEC 开头的密钥 |
| `DEEPSEEK_API_KEY` | 可选，在 [DeepSeek 平台](https://platform.deepseek.com) 获取；用于文字简报和主图识别。未配置时使用模板简报和已有的非视觉依据 |

## 部署到 GitHub

1. Fork 仓库并在 **Actions** 页启用工作流。按上表添加仓库 Secrets。
2. 在 **Settings → Pages → Build and deployment** 中，将 Source 设为 **GitHub Actions**。
3. 打开 **Actions → 家具爆品雷达 → Run workflow**，`mode` 选 `run`。可用 `force` 忽略运行间隔、`notify` 控制钉钉推送、`budget` 覆盖本期调用预算。
4. 完成后在钉钉卡片中打开报告。之后每天检查、满 14 天运行；首次运行及补齐历史名单时，耗时取决于调用数量、限流和主图识别量，以 Actions 进度为准。

Windows 用户也可安装 [GitHub CLI](https://cli.github.com)，执行 `gh auth login` 后，在仓库目录运行密钥配置脚本：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\setup_secrets.ps1
```

脚本可读取本地 `.env`；缺少 `REPORT_KEY` 时会生成并保存到 `.env`，请备份。

**添加更多钉钉群**：每个群新增一个 Secret，名称使用 `DINGTALK_ROBOT_1` 至 `DINGTALK_ROBOT_5`，值为 `Webhook地址,SEC密钥`。可与原有 Webhook 配置同时使用；删掉对应 Secret 即停止向该群推送。工作流已预留 5 个，更多群需同步修改工作流。本地支持 `DINGTALK_ROBOT_<名字>`。

### 常用操作

| 命令或操作 | 用途 |
|---|---|
| `python -m radar run --force --notify` | 忽略运行间隔，真实采集并推送钉钉；会消耗卖家精灵调用 |
| `python -m radar rerender` | 用已保存数据重生成最近一期报告，不调用卖家精灵，报告链接不变；线上在工作流中选 `mode: rerender` |
| `python -m radar notify` | 将最近一期报告推送到钉钉 |
| `python -m radar test-dingtalk --with-key` | 发送测试卡片，检查机器人及链接密钥片段是否保留 |
| `python -m radar status` | 查看本地期数、调用记录和历史数据概况 |
| `python -m radar decrypt site/reports/某期日期.html` | 将报告解密到本地；也支持 `site/data/state.enc` |
| `python -m radar reseal` | 重新加密，内容和链接不变；用于 GitHub 推送保护误判密文时的恢复 |
| `python -m radar --help` | 查看全部命令；各命令后加 `--help` 查看参数 |

验证代码时先运行 `python -m pip install -r requirements-dev.txt`，再运行 `python -m pytest -q`。测试不会调用真实卖家精灵或钉钉。

## 常用参数与预算

所有非机密配置见 [config.yaml](config.yaml)，密钥放 `.env` 或 GitHub Secrets。

| 配置项 | 调整内容与当前默认值 |
|---|---|
| `scope.*` | 类目范围、标题排除规则、额外追踪类目 |
| `pool.*` | 追踪名额、全市场门槛和初筛条件；降低门槛会增加调用需求 |
| `schedule.min_days_between_runs` | 运行间隔，默认 14 天 |
| `budget.split`、`monthly_cap`、`max_per_run` | 默认 `even`：本月剩余额度按剩余期数分配；每月上限 2,000、本期上限 2,500。`per_run` / `bootstrap_run` 仅在 `fixed` 模式生效 |
| `budget.review_checks`、`review_checks_unlisted` | 每期核查总名额 15 个（含评论和详情）；其中预留 5 个给未上榜、已有单条信号的商品，候选不足时归还其余核查 |
| `budget.material_lookups`、`monthly_list_calls` | 每期材质查询最多 30 次、往月名单补齐最多 50 次 |
| `thresholds.*` | 评分、爆火、潜力、热销、异常、数据时效、外观工艺和开发方向等规则 |
| `llm.*` | 文字简报、主图识别开关及模型；识别结果会缓存，模型费用另计 |
| `report.*`、`notify.*` | 报告标题、网址、保留期数及推送内容；默认保留最近 60 期报告 |

调用次数按北京时间的自然月记账。首次运行需发现类目、建立基准，往月名单会分期补齐；之后按预算优先追踪上期上榜商品、子类目头部和初筛机会。实际覆盖数量随市场及预算变化，报告的数据说明会列出当期覆盖情况。

若与 AI 工作台共用卖家精灵密钥，账户额度由两边共同消耗；本项目只记录自身调用，配置预算时需为其他用途留出额度。

## 失败恢复与常见问题

| 情况 | 处理方式 |
|---|---|
| 本期没有生成报告 | 查看 Actions 日志或钉钉告警。核心阶段额度耗尽、持续连接失败、刷新比例不足、整批数据过期或程序错误时停止发布；已获取的数据及调用次数会保存，旧报告保留 |
| 下次运行如何接续 | 复用仍有效的已获取数据；整批过期数据会重新拉取。已保存更新数据但尚未发布新一期时，暂停 `rerender`，待正常出新一期后恢复 |
| 只想更新报告样式或规则 | 线上运行 `mode: rerender`，按原报告日期重生成；不会重新采集数据 |
| 有爆品没出现在报告 | 检查类目、标题、评分、全市场门槛和本期预算覆盖；刚起量或短期增长商品可能尚未进入名单或追踪池 |
| 钉钉加签或关键词错误 | 核对 Webhook 与 SEC 密钥是否属于同一机器人；使用关键词模式时设置关键词“雷达” |
| 报告打不开或网址需更换 | 检查网络和链接密钥；使用自定义域名时，线上在仓库 Actions **Variables** 设置 `REPORT_BASE_URL`，本地在 `.env` 设置同名变量 |

## 数据与密钥保护

- 源码放在 `main`，线上加密状态和报告保存在 `site` 分支；发布的网站不包含 `data/` 目录，首页只列报告日期。
- `REPORT_KEY` 是主密钥，每期报告有独立密钥，位于链接的 `#k=` 片段。该片段不随页面请求发送给服务器；打开报告后会从地址栏移除。分享链接即授予该期报告的访问权限。
- 往期报告从对应钉钉消息打开，也可在报告页手动输入密钥。**丢失主密钥后无法恢复历史数据，不能直接换一把新密钥继续解密旧数据。**
- `.env`、本地数据和输出目录已被 Git 忽略；解密导出的明文也应保留在本地。公开 Actions 日志仅输出汇总，调试时避免打印商品数据或密钥。
