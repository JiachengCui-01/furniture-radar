# 家具爆品雷达

基于卖家精灵数据监控美国站家具，识别增长、持续热销和异常商品，形成开发方向，生成加密报告并推送钉钉。

每14天运行一期，每月调用上限2,000次；每天北京时间08:17检查是否到运行日期。参数见 [config.yaml](config.yaml)，离线说明见 [Word规则手册](判定规则说明.docx)。

## 判断规则

以下规则适用于每次采集、判断和发布。先说明术语与比较对象，再列触发条件和处理结果；各板块阈值须与配置、实现一致，变更时同步报告说明和两份文档。

## 1 术语与商品归类

筛选门槛、样本下限和调用配额的用途各不相同；“取值理由”说明设计取舍，不代表行业标准或最优值保证。调整时须同时检查误入和漏选。

### 先明确比较对象

| 术语 | 本项目中的含义 |
|---|---|
| BSR | 亚马逊商品销售排名，数字越小越靠前。只比较同一排名口径；从1,000降到500表示排名改善，不代表销量翻倍 |
| ASIN、父体、变体 | ASIN是商品编号；同款不同颜色、尺寸等变体可归同一父体。按父体去重，就是同一家族只算一个商品 |
| 数据截止日、判定日 | 截止日是商品日数据最后覆盖的日期；判定日是这期报告采用的业务日期。所有“近7/14/28天”须以指定截止日向前计算，不能随打开报告的日期移动 |
| 日均销量 | 参与计算的销量合计÷有效天数。缺失不当零；哪些日子要排除，见第2节 |
| 中位数 | 数值从小到大排列后取中间值；偶数个取中间两个的平均值。用来减少个别极端值的影响 |
| 销量倍数 | 近期日均÷对比期日均。例如从10件/天增到20件/天，是2倍，也就是增长100% |

### 主标签是归类优先级

一个商品可以同时符合多种条件，但只能有一个主标签。须按 **评分偏低 → 异常 → 突然爆火 → 潜力 → 持续热销 → 观察** 的优先级归类；这是主板块的选择顺序，其他条件仍可计算并保留为附加标签。

例如，低评分商品即使销量暴涨，主标签仍为评分偏低；评分合格但异常分达线的爆发商品归异常；同时符合爆火和热销的商品归爆火，可附“长期头部”。这样可避免风险商品混入正向推荐，也避免重复计数。

“上升中”是观察或热销商品的附加标签，不重复统计已归爆火、潜力的商品。**增长商品 = 突然爆火 + 潜力 + 上升中**，用于后续外观分析和开发方向；低评分和异常商品不得进入这批样本。文字简报只总结程序结果，不得决定分类、分数或金额。

实现：[分类、样本与排序](radar/analyze.py)。

## 2 采集范围与比较口径

### 哪些商品进入候选

范围限美国站家具、办公家具中的板材、实木、铁木柜桌、床架和置物架，排除沙发、床垫、椅子、软包、布艺抽屉、塑料和配件。子类目名称须通过保留词、排除词检查，商品标题再检查；面料词结合品类，配件词结合家具名词位置判断。子类目商品数须至少800，最多追踪30类。

**取值理由：** 800是类目容量门槛，减少过窄类目；30类限制采集成本，把预算集中在适合开发的市场。

机会候选须满足 **近30天销量至少300件，或销售额至少4万美元**，按父体去重。然后满足以下任一初筛条件：相比约28天前保存的近30天名单，销量增长至少15%；上架不超过180天且销量未跌；或用相隔约14天的两份名单估算短期日销，达到较早名单日均的1.3倍。新进名单没有旧记录时可保留候选，不能直接认定它以前零销量。

无合适基准时，可用上月名单或21～52天前快照。按距报告日的天数分档：21～23天增长线10%，24～36天15%，37～52天10%；月度基准下，名单给出的近7天BSR改善至少20%也可触发初筛。月销量先按该月天数折算为同一口径，更换代表子体须按父体匹配。短期日销是名单差额估计，只用于初筛，正式入榜必须再查日数据。

**取值理由：** 300件/4万美元兼顾走量款和高价款；15%增长、1.3倍短期放量与分档10%是候选触发线，采用“任一满足”先保留机会，再由日数据过滤误入。

预算按以下顺序分配：上期爆火、潜力、异常最多300个 → 子类目头部30个 → 初筛机会，总池上限3,000。新进名单中近7天BSR改善至少20%的优先，其余综合旧基准增长和短期持续性排序。月度发现取每类销售额前50；新品补查取销量最大的12类，每类最多30个、月销售额至少2万美元。

同类目相邻两个月有至少5个共同商品，其中至少50%的月销量完全相同，须标记名单可能尚未更新完，重拉受影响类目；不能把名单未更新解释成销量稳定。

**取值理由：** 至少5个且一半相同，要求重复有一定规模，避免一两个巧合就反复重拉；发现榜单和追踪名额用于控制调用量，不是入榜证据强弱的标准。

### 窗口与数据有效性

- **评分**：一般至少4.0分；已知评论数少于100条时至少4.2分。无评分不直接当低分，评论数未知时用4.0线。评分优先取最近日数据，缺失再用名单。
- **日期**：日数据落后“批次最新数据日、判定日”中较晚者超过2天，不判爆火、潜力或上升中；整批都过期时停止发布。实际刷新商品数须达到计划的60%，且至少1个。
- **近期与对比期**：爆火用最近7或14天，分别与紧接在它之前的28天比较；潜力、上升中用最近28天与再之前28天比较，两段不重叠。不能把“上期报告”当成固定的旧28天窗口。
- **缺失与明确零**：没有数据代表未知，不能补成0。对比期有有效在卖数据时按其均值；过滤后没有在卖数据时，只有至少7个明确零日、其余非大促有效销量也全零，才能补认零基准。
- **自然月**：热销及潜力月趋势只看已经结束的月份。缺月保留空位，不拿更早月份补齐。月趋势估计整段的平均每月变化速度：按真实月份间隔对ln(月销量+1)拟合后换算，不是逐月涨幅逐个过线；不足2个有效月不计算。新品累计销量另按第6节处理。

**取值理由：** 4.0是质量底线，评论少于100时用4.2留出波动余量；2天容许短暂延迟，60%防止少量新数据撑起整份报告。7/14天看起量速度，28天覆盖4个周周期，减少单周偶然性。

### 对比期怎样排除疑似断货

目的是比较商品正常销售时的水平，避免把恢复供货误判成新需求。**剔除只影响计算，不删除原始记录，也不把近期低销量隐藏掉。**

1. 计算旧对比期日均时，跳过BSR缺失或达到1,000,000的日子，按疑似未正常在售处理；这不是库存确证。
2. 潜力、上升中还跳过连续至少3天明确零销量的整段。连续性按原始日历判断：零、零、零的中间一天即使是大促，也仍是连续3天。
3. 最近7/14/28天日均保留有效的低销量和零销量。统计旧期在卖天数时，大促日只要符合在卖条件仍计入；比较日均时则跳过确认的大促日。
4. 旧对比期有效在卖不足14天，须标注天数，但不一律取消增长分类。仅哪些月增量须归零，见第9节。

**取值理由：** BSR百万线和连续3个零日提供两种停售线索；至少7个明确零日才补认零基准，可减少把缺数当从零起量。14天代表旧28天的一半，用于提示基准偏短。

例如，旧28天断货20天，其余8天每天10件；近期也每天10件。正常销售水平是10件对10件，不能用含断货日的低均值制造增长倍数。

### 大促、大盘与销量修订

**大促日**：先选前14天至少70%有数据、销量中位数至少3件的商品。当日合格商品至少40个，其中至少30%的销量达到自身基准1.8倍，才认核心大促日；相邻日冲高占比至少15%可延伸，登记活动也须有15%的数据印证。日度比较排除确认的大促日，不额外作季节调整。

**取值理由：** 70%覆盖和40个样本减少缺数、小群体干扰；1.8倍与30%同时要求放量幅度和普遍性，15%用于接住大促前后的较弱延续。

**大盘倍数**：同类目至少10个共同商品，把各自销量变化统一折成28天跨度后取中位数，最高按2倍。若大盘上涨，增长商品的销量倍数先除以大盘再过线；例如商品3倍、大盘1.5倍，按2倍检查。大盘下跌不放宽门槛，从零起量没有普通倍数、不作相除。

**销量修订**：先比较同一批商品、同一天销量在先后两次获取中的变化，至少30个共同商品、历史下调至少2%，才估计下调系数和受影响的近期天数。系数是改后销量÷改前销量，例如0.8表示改为原数的80%。

还须确认近期是否偏高：对同一批商品，算“最近受影响天数的日均÷再之前18天日均”并取中位数；把日期整体前移14天再算一次，用前者除以后者。前后都须有有效比值，共同商品至少30个；结果达到`1+(1/历史下调系数−1)×0.5`才确认。例如系数0.8，确认线为1.125。

`correct`模式仅在两步都通过时，将对应最近几天销量乘下调系数，再重算分类和金额；证据不足保留原值并提示。`tag`模式只提示校正可能带来的变化，不改金额和排序。

**取值理由：** 大盘至少10个、最高2倍，避免个别商品或极端值过度抬高增长线；修订至少30个、下调2%，避免小范围抖动触发校正。确认线取历史偏高幅度的一半（0.5），在漏检与误校正间折中，不是只校正一半销量。

参数：`scope`、`discovery`、`pool`及`thresholds`通用项。实现：[采集与初筛](radar/universe.py)、[日窗口](radar/series.py)、[大促](radar/detect/events.py)、[综合判断](radar/analyze.py)。

## 3 突然爆火潜力与上升中

三类均须通过评分、异常及时效检查，并排除已识别的断货恢复、短时脉冲和近期回落。这里的“排除”是不能进入增长样本；商品原始记录仍保留。

### 突然爆火

最近7天和最近14天分别完成全部检查，任一窗口合格即可；若两者都合格，选爆发强度较高的一组展示。不能先选最高倍数，再让该窗口的失败掩盖另一窗口的合格结果。

普通增长须**全部满足**：近期日均至少3件；近期日均÷旧28天在卖日均至少2倍；近期BSR中位数÷旧期BSR中位数不超过0.5；大盘上涨时，扣大盘后的销量倍数仍至少2倍。

旧基准已知且日均低于0.5件，改走“从零起量”：日均须达到30件与“第4节类目月销量门槛÷30×25%”中的较高值。没有旧BSR可不要求排名改善，有旧BSR仍须检查。上架不超过180天称新品爆发，超龄或年龄未知称老链接重新起量；已识别老品换链接不得走此通道。

放量还须通过持续性检查。取最近7个非大促日，最多往前查14个日历日：

- 先算每天超过旧基准的正增量；最大的2天贡献至少60%时，认作短时脉冲，不能确认爆火，从零起量也一样。
- 排除脉冲后，从零起量可确认；普通增长还须符合以下任一形态。
- **稳在高位**：至少5天销量达到旧基准的1.5倍，最近3天日均为这7天日均的0.85～1.15倍。
- **仍在上涨**：这7天日均至少是前7个非大促日的1.15倍，且这7天中最后3天日均高于整段日均。

不符合上述形态则不算爆火。近期价格中位数比旧期下降至少15%，只标“降价驱动”，不单独取消入榜；量未达确认线只作起量提示。

**取值理由：** 日均3件防小基数，销量2倍、排名改善一半要求明显变化；从零起量改用30件和类目25%双规模线。2天占60%排尖峰，7天中5天达1.5倍检验持续性，±15%容许走平波动，周增15%确认仍在抬升；降价15%用于提示价格驱动。

### 潜力与上升中

两类均使用“旧28天在卖日均”作分母；先检查最近28天，再检查最近7个非大促日（最多回看14日），**两个倍数都要达线**。基准未知或为零时不能用无限倍数通过。

| 条件 | 潜力产品 | 上升中 |
|---|---|---|
| 上架与评论 | 上架30～180天；已知评论数少于300条，未知不直接判超线 | 不限年龄和评论数 |
| 最近28天日均 | 至少2件 | 至少3件 |
| 两项销量倍数 | 扣上涨大盘后均至少1.2倍 | 扣上涨大盘后均至少1.3倍 |
| 月趋势 | 最近3个已结束月中，上架月之后有至少2个有效月时，整段拟合的平均月增长率须至少15%；月份不足只标“尚未验证” | 不要求 |
| 其他限制 | 不得是老品换链接 | 只附加于未归爆火、潜力的观察或热销商品 |

**取值理由：** 30天先积累观察，180天和300条评论限制成熟度；潜力用2件、1.2倍捕捉较早增长，上升中不限年龄，改用3件、1.3倍要求更明显。月增15%检验跨月延续，最近一周再过线防止旧涨幅撑榜。

例如，近28天增长50%，但最近一周已回到旧基准的1.05倍，潜力和上升中均不成立。爆火、潜力先按月增量排序，同额分别看爆发强度、增长幅度；增量怎么算、何时归零见第9节。

参数：`thresholds.surge`、`potential`、`rising`。实现：[准入与形态](radar/detect/rules.py)、[窗口筛选与排序](radar/analyze.py)。

## 4 持续热销

持续热销表示有规模且较稳定，不要求近期还在增长。类目门槛取销售额、销量头部名单合并、按父体去重后的月销量第20名；不足20个取末位，无样本不设门槛。这是采集样本门槛，不能表述为每个历史月的全市场真实排名。

以下条件须**同时满足**：

1. 最近4个已结束自然月至少3个月月销量达到类目门槛；每个计入的月份还须销量至少150件，或销售额至少2万美元。
2. 最近6个日历月已知月销量的CV不超过0.35。CV=标准差÷均值，越小越稳定；缺月仍保留位置，不要求6个月都必须有值。
3. 最近3个月能算趋势时，整段拟合的平均月趋势不低于−15%；趋势无法计算不单独否决，但其他条件仍须满足。
4. 最近28天日均至少达到上述6个月“已知月份平均日均”的70%，防止只凭过去成绩入榜。

**取值理由：** 类目前20提供相对规模标尺，150件/2万美元防小类目门槛过低；4个月中3个月达标可容一月波动。CV 0.35限制波动幅度，月趋势−15%和近期70%允许适度起伏，排除明显衰退。

按6个月已知月销量的平均值降序。近期回落可保留热销、附回落提示，但不得因此继续算作增长。

**只有月度数据时补判**：商品未被日数据追踪、与已追踪商品不同父体、连续6个月都在对应类目销售额或销量前50，才进入补判。还须有报告期有效近30天销量，用销量÷30估计近期日均，再按大促、修订口径及上述热销条件判断。

月度补判不得画日走势图、判断日度回落或计入日数据追踪数。若留评率、有效评论核查等使异常分达线，须转入异常、标“长期头部”，不再计热销数量。

**取值理由：** 没有日数据时要求连续6个月入头部，用更长历史补足持续性证据，同时保留近30天检查，避免只看老成绩。

参数：`thresholds.hot`。实现：[热销条件](radar/detect/rules.py)、[月度补判](radar/analyze.py)。

## 5 回落断货恢复与老品换链接

### 哪些走势算近期回落

以下任一成立，就取消爆火、潜力、上升中；持续热销可保留并提示。销量比较跳过大促日，缺失不补零：

- 最近3天日均低于近28天最高连续3天日均的75%，**并且**低于再之前3天日均的90%。两个条件须同时成立。
- 最近7天销量中位数低于再之前7天中位数的85%。
- 近7天峰值后至少连续3个有效观察日未回升，最后一天销量不超过峰值的70%。

**取值理由：** 75%与90%同时检查“明显低于峰值、还在继续下降”；周中位数85%检查整周走弱，连续3次且跌到70%补抓快速下滑，减少单日噪声。

### 怎样认定断货恢复

须同时有三类证据：爆火旧基准期明确零销量或BSR达断货线的日子，不少于7天且不少于有效窗口长度的25%；再往前90天有至少14个非零销售日；这些更早销售日的日均至少是近期日均一半。满足才将放量视为恢复供货，排除增长；缺数据不能代替断货证据。

**取值理由：** 一周/四分之一确认断货已明显压低基准；90天内至少14个销售日、达到近期一半，要求有持续且相近的旧销售水平，避免把零星历史当恢复。

### 怎样识别老品换链接

该标签表示新链接可能继承老链接的评论或销售基础，不能仅凭上架时间短当成真新品。须上架不超过180天，并满足：

- 累计评论÷本ASIN已观测累计日销量达到50%；**或**
- 上述比例达到15%，并有以下任一证据：开卖首周日均至少5件且至少为最近7天日均一半；首次达到“5件、最近7天日均一半”中较高量级后，随后一周仍达到该量级、前一周日均不超过后一周10%；有效抽查的近60天评论量不到按累计评论和上架天数折算应有量的一半。

识别后不判潜力或从零新品爆发，也不以继承评论给留评率、新品评论比加分；仍可凭自身稳在高位、上涨或上升中证据入选。对比期涉及开卖首周只标注，月增量是否归零另按第9节判断。

**取值理由：** 50%设置较强的评论存量门槛；15%则必须再有快速满速或评论继承证据。5件/近期一半及前后10%约束跳变，减少把正常广告起量的新品误判为换链接。

参数：`thresholds.momentum`、`relist`、恢复项。实现：[回落恢复与换链接](radar/detect/rules.py)。

## 6 异常信号怎样计分

异常分表示人工复核优先级，不是刷单概率。**总分至少3分进异常榜，至少5分列为较高风险**；按总分、近28天日均降序。同一商品低评分时优先归低评分。不得因空榜认定没有异常，也不得为填榜降低证据要求。

留评率指名单对应统计期的新增评论÷该期销量；新品评论比看累计评论与累计销量，评论增速看两次观察之间新增评论与同期销量，三者比较时间不同。它们都在衡量“评论相对销量过多”，重叠时须按下表降权。

| 信号 | 触发条件 | 分值 |
|---|---|---|
| 留评率偏高 | 扣Vine后新增评论至少10条；留评率同时达到6%和类目中位数3倍 | +2 |
| 新品评论比 | 上架不超过90天、总评论至少20条；扣Vine后累计评论÷完整累计销量至少10% | +2；留评率已加分则只+1 |
| 评论增速偏高 | 扣Vine后新增至少10条；同期完整销量为零，或新增评论÷同期销量同时达到15%和类目留评率中位数3倍 | +2；前两项任一已加分则只+1 |
| 评分跳升 | 相比45天内前次有效观察，评分提高至少0.2，总评论至少50条 | +1 |
| 销量脉冲 | 近30天内出现1～3天冲高，起点达到前28天销量中位数3倍且至少6件/天；之后至少间隔3天、最多看7天，已有销量的日均回到基线1.3倍以下；不在大促日 | +1 |
| 评论集中 | 样本至少10条，评论最多的3天合计至少占30%，且条数超过同样样本量、跨度下随机分布的99%参考上限 | +2 |
| 非验证购买多 | 至少10条评论明确记录了验证购买标记，其中未验证购买至少占50% | +1 |

**取值理由：** 2分用于较强的评论比例/集中信号，1分用于辅助信号，3/5分区分复核优先级。6%与类目3倍兼顾绝对、相对异常；10%/15%要求明显偏高，10/20/50条及0.2分变化减少少量评论触发；非验证达到一半也只加1分，避免单项定性。

评论集中须同时满足占比和随机参考上限，防止少量评论天然集中造成误报。“最多的3天”不要求连续3天；99%参考值也不表示99%概率刷评。

### 哪些证据不能加分

- 评论和销量须来自同一父体范围，不得再除以变体数。名单新增评论超过“总评论×1.05+5”，说明口径可能混用，该留评率不计。有效核查表明评论继承或已识别换链接时，对应留评率、新品评论比也不计。
- 评论增速的旧评论数取此前45天记录最高值，没有才用前次有效观察。例如100→80→95不是新增15条。确认父体/变体合并时，相关评论增速不计。
- 两次评论观察之间的销量须每天完整、非负且不是无效数；缺一天就不算该比率。只有明确全零才能计“有评论、无销量”。新品累计销量须覆盖上架月至截止月，包括截止月已有销量；月度不齐再查上架日起完整日数据，仍不齐则不计，未来月份忽略。

### Vine怎样扣除

Vine是亚马逊测评评论，不能直接当异常评论。有效核查能给出Vine比例时，按实际样本估计应扣量；无可用比例、上架不超过90天时，对累计前30条评论作可能Vine的保守扣减。30是项目参数，不表示平台政策。

当期留评率、累计新品评论比、观察间评论增量须各按对应时段扣除，不能每次给新增评论重复减30条。扣前达异常条件、扣后未达线的新品仍须保留待核查资格。Vine样本占比至少30%、变体合并、大促脉冲只加解释标签，不加异常分。

**取值理由：** 99%采用较保守的随机参考上限，减少小样本误报；90天内预留30条可能Vine评论，给正常新品测评留余地，取得有效核查后再用实际比例。

参数：`thresholds.fake`。实现：[计分与抵扣](radar/detect/fakehot.py)、[完整销量区间](radar/series.py)。

## 7 评论核查怎样使用

每期最多15次补查调用，评论查询和父体/变体详情查询共用总额；其中预留5次给未上榜、异常分至少2分的候选，不足再归还其他核查。一次调用不是一条评论，也不保证一个商品所有补查都做完。

评论数相对前次上涨至少30%、又缺有效详情核查时，先检查父体/变体。其他评论查询依次看：可疑上榜商品 → 报告点名与开发参考候选 → 未上榜且至少2分 → 其他爆火/潜力 → 可能Vine扣减新品。同级综合异常分、增长强度和销售额安排，仍须保障预留名额；排不上不能视为已通过核查。

### 样本有效性

评论样本是实际抽查到的评论，可能只占全部评论的一部分；抽到多少条、总共有多少条须分开记录。

- 查询与返回过滤必须采用同一截止日，取此前约60天的最新评论。只抽到部分评论时，集中度用“最早样本日至截止日”的跨度，至少7天；确认近60天评论已取全时按60天。返回内容被日期过滤后全空，不保存为一次新的有效核查。
- 验证购买只认明确真/假，没字段不当作未验证。至少10条有明确标记才算非验证比例；Vine标记须覆盖全部抽样评论才用比例。
- 零条样本但总量非零或未知，不能证明没有评论。复用旧核查时，缺标记样本数的比例不得沿用；仍有依据的条数、集中度可保留。

### 时效与身份

核查取得日到判定日须为0～13天，满14天失效；若记录了评论样本截止日，该日相对判定日、商品数据日中较晚者也须在0～13天内。取得日表示“何时查到”，样本截止日表示“查到哪个日期”，必须分别保存。

核查须绑定当时的父体、变体结构，这就是商品身份。父体改变，或变体数量变化达到“2个、旧数量30%”中较高值，原评论核查失效。例如旧10个变体，变化至少3个才达线。详情核查须留前后结构，更新父体前保留旧快照；同日评分变化须保存，缺字段不得覆盖已有有效值。

历史回放是用保存的数据重新判断过去一期；只能用当时已经取得的核查和当时身份，不得使用后来查询的结果来给过去加分或豁免。

**取值理由：** 15次中留5次，防止未上榜候选长期得不到复核；14天有效期与运行周期配合，避免旧证据长期沿用。60天与至少7天的样本跨度用于比较集中度；变体变化须同时达到2个和30%，过滤微小结构调整。

参数：`budget.review_checks`、`review_checks_unlisted`。实现：[核查分配与样本](radar/verify.py)、[时效与身份](radar/evidence.py)。

## 8 外观工艺与主材质

### 先分清两种对照

标题共性比较“增长商品”与“全部月度头部商品”，至少需要3个增长、20个头部。主图取势头前50个增长，对照最多40个不属于增长的持续热销商品，另补开发方向所需识别样本。两种来源须分别说明，颜色有主图时优先主图。

每项外观特征须至少2个增长商品、2个已知品牌支持。品牌未知的商品可保留在商品占比分母，但不能把不同ASIN冒充不同品牌。

| 分档 | 判断条件 | 可说明什么 |
|---|---|---|
| 更多 | 标题中该特征占增长商品至少10%，且修正后的占比至少是头部1.3倍；或主图中增长侧比对照高至少10个百分点 | 在对应样本中相对更突出 |
| 常见 | 未入更多，增长侧该特征占比至少30% | 多个增长商品共同具有，不表示比对照更多 |
| 也有 | 未入前两档，增长侧占比至少10% | 有一定支持，证据弱于常见 |

“高10个百分点”指40%减30%得到10个百分点。标题占比倍数用小样本修正：两组计数各加0.5、样本数各加1，再求占比和倍数，避免头部计数为零就变成无限倍数。

若有效标题说更多、有效主图说更少，或反过来，该特征三档都不列。更多按占比差排序，两源共同支持适当前置；每个维度最多6个更多、3个常见、6个也有。

其他结构化共性须至少2个商品、增长占比至少20%、修正后的占比倍数至少1.5，最多10条。关键词通常至少3个商品支持；增长样本少于20时，用“2、样本量15%向上取整”中较大值，修正倍数至少2，最多15条。它们表示共现，不能解释成特征或词语导致销量增长。

### 主材质单独统计

每商品只取一个主材质，证据顺序为 **商品Material材质属性 → 标题明确材质 → 主图识别 → 标题笼统木质**。木纹不能直接判实木，缺属性不能当作没有该材质。

增长与持续热销须分组统计材质构成，未知类别保留在分母，不能直接套外观“更多”结论。每期材质属性查询最多30次，引用时注明来源，不能把尚未查询的商品说成已核实材质。

**取值理由：** 2个商品、2个品牌减少单卖家重复铺款影响；10%占比加1.3倍、或高10个百分点，要求有覆盖也有差距。30%“常见”和10%“也有”区分支持强弱；50/40识别名额与各维度展示上限用于控制成本和阅读量，不代表统计保证。

参数：`thresholds.appearance`、`llm.vision_*`。实现：[标题特征](radar/detect/design.py)、[共性合并](radar/detect/traits.py)、[主材质](radar/materials.py)。

## 9 开发方向增量与成本

### 哪些类目形成方向

同类目至少2个增长商品、2个已知品牌，才形成候选方向。按月增量总额降序，同额依次看品牌数、增长商品数、爆火数和势头。报告按配置上限展示，0表示全部，摘要前5；没有共同特征和明确材质时不得拼凑画像，须列原因，高增量缺画像另提示。

### 怎样和同类目头部比较

头部取该类月销量前30，排除增长商品及其同父体商品。头部至少10个已知品牌才作相对比较；其中已识别主图的品牌也达到10个时，两边都用标题+主图，否则两边都只用标题。头部不足10个品牌时，只列共同特征，不能声称比头部更多。

为防一个品牌上很多相似款主导结果，先算品牌内部有该特征的商品比例，再对品牌等权平均。例如A品牌5/10个有，B品牌1/1个有，品牌均占比是(50%+100%)/2=75%。

- **比头部多**：至少2个品牌支持，增长侧品牌均占比比头部高至少20个百分点，且至少为头部1.5倍。
- **基本款**：至少2个品牌支持，增长侧品牌均占比至少50%，且没进更多。没有充分头部对照时称共同特征。每个维度每档最多3项。
- **主材质**：一个品牌任一增长商品有该材质，就算该品牌支持；至少半数已知品牌且至少2个品牌支持才列，不直接说成头部优势。
- **价格与参考**：价格取有效售价的最低～最高值，至少3个有效价格才给中位数。参考最多2个，须异常分为0且来自不同已知品牌；不足少列，0分也不等于已证实安全。

**取值理由：** 至少10个头部品牌再比较，降低单品牌偏差；高20个百分点且达1.5倍，排除品类普遍特征。50%用于识别多数品牌具备的基本款，双品牌参考减少重复；摘要5个、每档3项便于执行，完整证据仍保留。

### 月销售额与月增量怎么算

估算月销售额 = 最近28天日均×商品售价×30。

估算月增量 =（最近28天日均−再之前28天在卖日均）×同一售价×30。

两项统一大促和修订口径。未知基准须显示“无法估算”，不计合计；能按公式计算的负增量保留，但以下情形按0计增量，并写清原因：

1. 已识别老品换链接，旧28天没有在卖基准或在卖不足14天；若基准本身未知，仍优先标无法估算。
2. 从零起量但归“老链接重新起量”；或上架超过180天的老链接，旧28天在卖不足14天。
3. 增长只是回到旧高位：在旧基准开始之前56天内，找到有效在卖至少14天的历史连续28天最高日均；近期未超过它。爆火用选中的7/14天近期日均核对，其余增长用28天日均。
4. 没有售价，无法算金额。

这些归零只影响增量金额和排序，不自动撤销增长标签；因此增长商品也可能没有正的月增量。

**取值理由：** 旧28天至少14天在卖才有较充分的老链接基准；回看56天检查近期旧高位，避免恢复销量主导开发排序。乘30统一成月度量级，方便跨商品比较，不表示自然月实际收入。

### 包装与FBA费用

FBA这里指亚马逊配送费估算。必须用包装尺寸、重量，不能用组装尺寸代替；体积按英寸长×宽×高÷1,728得立方英尺，再×0.0283168得立方米，重量统一磅。

每项只按自身有值商品取中位数，所以体积、重量、费用样本数可以不同。FBA占售价先逐商品算，再取中位数。销量、金额和费用须标估算，利润还须另计采购、头程、佣金、仓储、广告、退货等成本。

参数：`thresholds.directions`、`short_base_days`、`recovery_days`。实现：[开发方向](radar/detect/directions.py)、[金额与归零](radar/analyze.py)、[包装费用](radar/shipping.py)。

## 10 上期对比与发布

### 上期变化怎样归类

- 依旧爆火：上期、本期主标签都是爆火。
- 新进入：本期进入某板块，上期不是这个板块；从其他板块转入须注明。
- 不再爆火：上期爆火，本期仍追踪但归观察或低评分。转潜力、热销、异常须在对应变化列出；本期未追踪不能当作回落。
- 月度补判：以前没覆盖、这期才靠历史名单判出热销，单列补判，不说成刚热销。对未追踪过的商品回看上期日期时，须标明回看；上期提示待修订时，须复核全部上期增长商品。

### 哪些数据问题只提示

增长商品变体数比旧记录增加至少30%且至少2个；近30天名单和日销量两边都至少60件，却相差至少2倍；最近28天缺至少7天日数据。遇到这些情况须提示数据风险，但不能直接替代各板块的判断。

若近10天出现广泛BSR改善：至少40个合格样本、过去排名中位数不高于30万，其中排名改善到自身旧值1/1.8的占比至少10%，连续至少2天，须提示销量可能还未修订；该提示本身不改分类。

### 预算与发布边界

运行间隔14天，每月调用上限2,000次；剩余额度按本月剩余期数均分，每期最多2,500次。评论和详情核查共15次、材质查询最多30次、月度名单补齐最多50次，均计入调用预算，不是额外免费额度。

按北京时间自然月记账，共享密钥须给其他服务留额度。核心采集失败、刷新不足、整批数据过期时，不得用残缺结果发布新一期；须保留旧报告和采集进度供重试。

**取值理由：** 14天周期与每月2,000次是时效、覆盖的预算折中；15/30/50控制补查对日数据名额的挤占。单期2,500是运行保护上限，仍受月度剩余额度限制。

实现：[上期对比](radar/detect/diff.py)、[数据标签](radar/analyze.py)、[发布流程](radar/pipeline.py)。

## 运行与部署

### 本地运行

安装Python 3.11，在仓库目录执行：

```powershell
python -m pip install -r requirements.txt
python -m radar demo
```

打开`out/demo/report.html`预览模拟报告，演示不消耗真实接口调用。真实采集前，复制 [.env.example](.env.example) 为`.env`并填密钥，再执行`python -m radar run`；已有`.env`直接编辑。本地`site/`保存本地历史，与GitHub线上数据分别管理。

| 密钥 | 用途与填写要求 |
|---|---|
| `SELLERSPRITE_SECRET_KEY` | 真实采集必填，在[卖家精灵开放平台](https://open.sellersprite.com)取得 |
| `REPORT_KEY` | 数据和报告加密必填，用`python -m radar keygen`生成，须备份 |
| `DINGTALK_WEBHOOK`、`DINGTALK_SECRET` | 推送时填写；在钉钉群添加加签机器人，分别填写Webhook地址、SEC开头的密钥 |
| `DEEPSEEK_API_KEY` | 可选，在[DeepSeek](https://platform.deepseek.com)取得，用于文字简报和主图识别；不填则使用模板简报及已有非视觉证据 |

### GitHub自动部署

1. Fork仓库并启用Actions，把上述密钥填入仓库 **Settings → Secrets and variables → Actions → Secrets**。
2. 在 **Settings → Pages → Build and deployment**，把Source设为 **GitHub Actions**。
3. 打开 **Actions → 家具爆品雷达 → Run workflow**，选`mode: run`。`force`表示忽略14天间隔，`notify`控制钉钉推送，`budget`覆盖这次调用上限。完成后从钉钉卡片打开报告。

Windows也可安装GitHub CLI，执行`gh auth login`后运行`powershell -ExecutionPolicy Bypass -File scripts\setup_secrets.ps1`配置密钥；脚本会读取`.env`，缺少`REPORT_KEY`时生成并保存。

多群推送：每个群新增Secret `DINGTALK_ROBOT_1`至`5`，值为`Webhook地址,SEC密钥`，中间用英文逗号；更多群须同步修改工作流。

| 目的 | 命令或入口 |
|---|---|
| 忽略间隔，真实采集并推送；会消耗调用 | `python -m radar run --force --notify` |

## 故障恢复与数据保护

- **没生成新报告**：检查Actions日志或钉钉告警。核心采集失败、刷新比例不足、整批过期时须保留旧报告；重试复用有效进度、重拉过期数据。若状态已有新数据但新一期还未发布，须先完成正常运行，不能直接`rerender`旧一期。
- **商品没有入选**：先查范围、量门槛、是否取得日数据，再查评分、时效、基准和排除原因。未覆盖与已覆盖但不达标须区分。
- **通知或报告链接失败**：先核对同一机器人的Webhook和SEC是否配对，再查网络、链接密钥。换域名用`REPORT_BASE_URL`：线上填Actions Variables，本地填`.env`。
- **存放与权限**：源码在`main`；线上加密数据和报告在`site`分支，公开站点不得含`data/`。报告链接的`#k=`后是该期解密密钥，分享完整链接即授予该期访问权限。
- **备份与提交**：必须备份主密钥`REPORT_KEY`，丢失无法恢复历史数据。`.env`、本地`site/`、`out/`和解密明文不得提交源码分支。密文触发推送保护时可用`python -m radar reseal`重新加密，更多操作见命令帮助。
