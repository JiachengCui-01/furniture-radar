# 家具爆品雷达

用卖家精灵数据查看美国站家具：哪些正在增长，哪些长期卖得稳，哪些需要核查，再整理成选品和开发方向。报告加密保存，可推送到钉钉。

每14天出一期，每月最多调用2,000次。每天早上检查是否到了运行日，时间见[自动任务](.github/workflows/radar.yml#L6)。

## 1 商品怎么归类

一个商品可能符合好几类，但只能放进一个主要板块。按下面的顺序，**符合前一类，就优先归前一类**：

**评分偏低 → 异常 → 突然爆火 → 潜力 → 持续热销 → 观察**

例如，销量暴涨但评分低，仍归“评分偏低”；评分合格但异常分达线，归“异常”；同时符合爆火和热销，归“爆火”，可以另标“长期头部”。这样不会重复计数，也不会把风险商品当正向推荐。

“上升中”是给观察或热销商品加的标签，不重复给爆火、潜力商品加。**蓝海产品**（第12节）是另一份名单，商品照样留在自己的板块里。后文的**增长商品，就是爆火、潜力和上升中这三类**，不含低评分、异常商品。报告的**本期要点**是四块图标卡片，除开发建议外都直接取计算结果：

- **外观与工艺趋势**：主材质、风格、造型、工艺、颜色、功能各一张卡，每张列几个特征——绿条是增长商品里的占比，竖线是对照组（主图比持续热销对照组，标题比全部头部商品），▲ / ▼ 是比对照明显多 / 少（差 ≥10 个百分点），金额是带这个特征的增长商品月增量合计。点一行弹出增长商品小窗，只看主图上看得出这个特征（或这种主材质）的商品；配图也只用主图上看得出的。
- **开发方向**：个数随本期增长变——月增量为正的子类目按增量从大到小，取到累计占全部方向月增量的80%为止（最多10个，`thresholds.directions.highlight_share / highlight_max`），钉钉消息同一组。卡片写月增量、比头部多的特征、售价中位和品类大盘，配图挑主图上看得出这些特征的增长商品，点开是下面一览同一个小窗。
- **开发建议**：大模型挑特征组合、参考商品和中文短名，代码逐条核对：特征须是本期增长商品更多、主图识别也多出≥10个百分点的（只在标题里多的不用），而且参考商品主图上看得出；参考商品须是列出的、没有任何风险标签的爆火或潜力。对不上的整条删掉；外观细节不用模型写的，取这张主图的外观要点里说到这些特征的句子。没有大模型时按同样的规则从数据里选。
- **风险提醒**：报告里列出的全部商品（各板块列出的和异常信号）身上的每一类风险因素各一组，一个商品可以在几组里：异常信号（和KPI同一批）、有可疑迹象（有信号但没到门槛）、降价驱动、数据可能有误、对比基准不足、老链接 / 断货恢复、大促 / 数据待修订、势头转弱、随大盘、只有月度数据；卡片上标红的标签归不进这些的写在“其他需要留意”。

大模型不能改分类、分数和金额。子类目中文名用`scope.node_names`里逐个核过的（卖家精灵自带的翻译有的不对，如Storage Cabinets叫“门厅收纳柜”，其实浴室、厨房、车库柜都有）；收纳柜这类用途不固定的子类目（`scope.room_nodes`），商品短称后面写标题里最先说到的房间，如“Minifeel 收纳柜 · 浴室”。这两项读的时候改，不算换监控范围。

对应代码：[归类顺序](radar/analyze.py#L304) · [增长商品范围](radar/analyze.py#L908)。

## 2 先查哪些商品，数据怎么算

### 哪些商品值得继续查

只看美国站家具、办公家具里的板材、实木、铁木柜桌、床架和置物架；排除沙发、床垫、椅子、软包、布艺抽屉、塑料和配件。先看子类目，再看标题；面料词要结合家具类型，配件词要看它在标题里的位置，不能见到一个词就直接排除。

子类目至少有800个商品，最多追踪30类。**为什么这样设：** 避免只覆盖很窄的小市场，也把采集成本控制住。

**小件不看。** 包装在亚马逊标准尺寸以内的商品——三边从长到短不超过18×14×8英寸，而且包装重量不超过20磅——在哪个子类目都剔除；没有包装数据的判断不了，不剔除。**衣帽架**整个子类目不追踪。

**为什么这样设：** 标准尺寸是亚马逊自己划的小件 / 大件分界，卖家精灵给的尺寸分段和它完全一致（10-23全覆盖试跑约1.1万个商品，一个不差）。11-01全市场名单3,855个商品里有515个是小件，主要在茶几（占这个子类目销售额的52%）、床头柜（23%）、玄关桌（18%）、书架（10%），其余子类目不超过6%。衣帽架2026年4～9月每个月的月度名单里67%～87%的销售额是小件，剔除小件后剩下的八九个也还是衣帽架，所以整类去掉；茶几、音响架只有一半左右是小件，剩下的是带抽屉、柜体的大号边几和影音柜，只剔除小件。按“小件占一半以上”自动去掉整个子类目不可靠：茶几每个月在45%～60%之间来回，床头柜也有一个月到过55%。这两条是读的时候过滤的，改了不用重新发现子类目。

对应代码：[类目筛选](radar/discovery.py#L159) · [商品标题筛选](radar/discovery.py#L83) · [小件](radar/discovery.py#L61) · [不追踪的子类目](radar/discovery.py#L77)。

商品先过规模门槛：**近30天销量至少300件，或者销售额至少4万美元，满足一个就行**。同一父体只留一个商品，避免同款的颜色、尺寸重复占名额。再满足下面任意一条，才继续查：

- 比约28天前保存的近30天名单，销量增长至少15%。
- 上架不超过180天，销量没有下降。
- 用相隔约14天的两份名单估算短期日销，达到较早名单日均的1.3倍。

新进名单没有旧记录，也可以先留作候选，但不能说它以前销量为零。

找不到合适的旧名单时，用上月名单或21～52天前的记录。旧记录距报告日21～23天，增长门槛10%；24～36天为15%；37～52天为10%。用月度名单比较时，近7天BSR改善至少20%也可以进入初筛。**BSR是销售排名，数字越小越靠前。**

不同月份先按各月天数换成可比的日均；代表商品换了颜色或尺寸，仍按父体匹配。**名单只能帮忙找候选，正式入榜还要查每天的销量。**

**为什么这样设：** 300件或4万美元兼顾走量款和高价款；15%、1.3倍及分档10%先留住增长机会，再用日数据排除误判。

对应代码：[初筛条件](radar/universe.py#L308) · [旧名单与短期日销](radar/universe.py#L263)。

### 先给谁查，名单有没有更新

采集名额按顺序安排：上期爆火、潜力、异常最多300个 → 子类目头部30个 → 蓝海产品最多40个（第12节）→ 初筛候选，总池最多3,000个。新进名单优先查近7天BSR改善至少20%的，其余结合旧名单增长和短期持续性排序。

月度发现取各类销售额前50；新品补查选销量最大的12类，每类最多30个，商品月销售额至少2万美元。

同类目相邻两个月至少有5个共同商品，其中至少50%的月销量完全相同，就提示名单可能没更新完，重新拉取该类目，不能直接说销量稳定。

**为什么这样设：** 至少5个且一半相同，避免一两个巧合就反复重查；采集名额是成本限制，不代表商品好坏。

对应代码：[名额分配](radar/tracking.py#L146) · [名单更新检查](radar/monthly_lists.py#L113)。

### 日期、评分和缺失数据怎么处理

- **评分**：一般至少4.0分；已知评论少于100条时，至少4.2分。没评分不直接算低分，评论数未知用4.0线。优先用最近日数据中的评分，没有再用名单。
- **数据够不够新**：先取“本批最新数据日”和“本期判定日”中较晚的一天。商品日数据比它落后超过2天，就不判爆火、潜力或上升中；整批都过期就不发布。本期实际刷新商品数还要达到计划的60%，且至少1个。
- **拿哪段时间比较**：以商品日数据最后一天向前算。爆火分别看近7天、近14天，与各自紧挨着的旧28天比较；潜力、上升中看近28天与再之前28天。两段不能重叠，也不能把“上期报告”当成旧28天。
- **缺数据不等于零销量**：旧期有正常在售数据，就用这些天的日均；没有时，至少要有7天明确记录为零，而且其余非大促日的有效销量也全是零，才能认作零基准。
- **按月看趋势**：只用已经结束的自然月，缺月留空，不拿更早月份补位。看整段平均每月涨多少，不要求每月都达标；计算会考虑真实月份间隔，不足2个有效月不算。新品累计销量另见第6节。

**为什么这样设：** 少评论商品用4.2分，多留一点质量余量；2天容许短暂延迟，60%保证覆盖。7天、14天便于及时发现增长，28天覆盖4周，减少单周偶然波动。

对应代码：[评分门槛](radar/detect/rules.py#L22) · [数据日期](radar/analyze.py#L283) · [刷新比例](radar/pipeline.py#L334) · [零基准](radar/series.py#L224) · [月趋势计算](radar/series.py#L184)。

### 旧期疑似断货的日子怎么算

要比较的是商品正常在售时卖得怎么样，不能因为以前断货，就把现在恢复供货当成新需求。**只从计算里排除相关日子，原始记录照留；近期的低销量、零销量也照算。**

1. 算旧期日均时，跳过没有BSR的日子，也跳过BSR达到或超过1,000,000的日子。这只是疑似未正常在售，不代表已确认断货。
2. 潜力、上升中还要跳过连续至少3天明确零销量的整段。按原始日历数，中间有大促也不打断连续性。
3. 旧期大促日如果正常在售，仍算在卖天数；但比较日均时，跳过已确认的大促日。
4. 旧期正常在售不足14天，要写清天数，不是一律取消增长资格。哪些情况月增量算0，见第9节。

**为什么这样设：** BSR百万线和连续3个零日用于找停售线索；7个明确零日防止把缺数当零；14天是旧28天的一半，用来提示旧数据支撑偏少。

例如，旧28天断货20天，其余8天每天卖10件，近期也每天卖10件，实际是10件对10件，不应算出增长。

对应代码：[疑似断货日过滤](radar/series.py#L81) · [在卖天数](radar/series.py#L97)。

### 大促和大盘上涨怎么处理

**大促日**：先选前14天数据覆盖至少70%、日销量中位数至少3件的商品。当日至少有40个合格商品，其中至少30%卖到自身平时水平的1.8倍，才认核心大促日。相邻日放量商品占比至少15%，可以连进活动期；手动登记的活动也要有15%的数据印证。比较日销量时排除确认的大促日，不另加季节调整。

**为什么这样设：** 70%覆盖和40个样本减少缺数、小群体影响；1.8倍加30%要求放量明显、涉及面够广；15%接住活动前后的较弱延续。

对应代码：[大促样本和放量占比](radar/detect/events.py#L26) · [活动日确认](radar/detect/events.py#L108)。

**大盘上涨**：同类目至少找10个共同商品，把各自销量变化折成28天跨度，再取中位数，最高按2倍。类目整体上涨时，商品增长倍数要先除以大盘倍数，再检查是否达标。比如商品3倍、大盘1.5倍，就按2倍检查；大盘下跌不放宽门槛，从零起量不这样相除。

对应代码：[大盘倍数](radar/universe.py#L352) · [扣除大盘后再判断](radar/analyze.py#L142)。

### 卖家精灵后来改了销量，怎么办

不能一看到历史数字变化就直接改近期销量，要先确认两件事：历史销量确实被下调，而且近期也有偏高迹象。

<details>
<summary>展开具体计算条件</summary>

1. 比较同一批商品、同一天销量在两次获取中的变化。至少30个共同商品、历史下调至少2%，才估计下调系数和受影响天数。系数=改后销量÷改前销量，例如0.8表示改为原来的80%。
2. 对同批商品，算“最近受影响天数的日均÷再之前18天日均”，取中位数；把日期整体前移14天，再算一次。前后都要有至少30个共同商品的有效比值。较近期的中位数÷前移14天后的中位数，达到`1+(1/历史下调系数−1)×0.5`，才确认近期偏高。例如系数0.8，确认线是1.125。

</details>

`correct`模式在两步都通过后，把受影响近期销量乘下调系数，重算分类和金额；证据不足就保留原值并提示。`tag`模式只提示可能变化，不改金额和排序。

**为什么这样设：** 大盘至少10个、最高2倍，减少个别商品或极端值的影响；修订至少30个、下调2%，防止小范围波动就触发校正。确认线取历史偏高幅度的一半（0.5），兼顾漏检和误校正；实际销量仍乘完整下调系数。

对应代码：[历史销量修订](radar/tracking.py#L367) · [近期偏高确认](radar/analyze.py#L636) · [销量校正](radar/analyze.py#L687)。

## 3 爆火、潜力和上升中

三类都要通过评分、异常和数据日期检查；已识别的断货恢复、短时冲高、近期回落不能算增长。原始商品记录仍保留。

**突然爆火和潜力按上架天数分开，两边不重叠**（分界是 `thresholds.potential.max_age_days`，90天）：

- **突然爆火 = 之前已经卖了一段时间、近期销量突然涨上来的**：上架超过90天。
- **潜力 = 近期新上架就卖得好的**：上架不超过90天。上架不到90天的，近1～2周达到了下面突然爆火的门槛，也算潜力（新品爆发 / 新品起量快），不算突然爆火。

已识别的老品换链接，上架天数不代表商品是新的：不算潜力；上架不到90天的也不算突然爆火（有上升中的照样标）。

**为什么这样设：** 以前两边按销量形态分、不看上架天数：11-02那期突然爆火22个里13个才上架11～87天，多是对比期只有几天在卖的开卖起量（例：上架11天的床架，对比期只有4天在卖）；潜力里7个已经上架122～180天。改成按上架天数分以后，突然爆火11个（都上架92天以上），潜力21个（都在90天以内：9个原来的“突然爆火”进来，8个上架100～180天的出去，照样标“上升中”、算增长商品）。90天是亚马逊新品榜和卖家常说的“新品期”。

### 什么算突然爆火

先要上架超过90天。近7天、近14天各自检查全部条件，**有一组全部通过就行**；两组都通过，展示爆发更强的一组，不能只查倍数最高的那组。

普通增长要同时满足：

- 近期日均至少3件。
- 至少达到旧28天正常在售日均的2倍，除以上涨的大盘倍数后也要有2倍。
- 近期BSR中位数不超过旧期的一半（0.5倍），也就是排名明显靠前。

旧数据已知、日均不到0.5件时，改看“从零起量”：近期日均至少达到30件，以及“第4节类目月销量门槛÷30×25%”，**两者取较高值**。有旧BSR仍要查排名改善，没有旧BSR可以免这项。上架不超过90天的叫“新品爆发”，算潜力；超过的叫“老链接重新起量”，算突然爆火；已识别老品换链接的不能走这条。

还要看放量有没有持续。取最近7个非大促日，最多回看14个日历日：

- **先排除短时冲高**：每天超过旧期日均的部分算新增量，如果最大的2天占了至少60%，就不确认爆火；从零起量也一样。
- 排除短时冲高后，从零起量可以确认；普通增长还要符合下面两种表现之一。
- **稳在高位**：至少5天卖到旧期日均的1.5倍，最后3天日均在这7天日均的0.85～1.15倍之间。
- **还在上涨**：这7天日均至少为前7个非大促日的1.15倍，而且最后3天日均高于这7天日均。

近期价格中位数比旧期下降至少15%，只标“降价驱动”，不因此取消入榜；销量还不够确认时，只提示开始起量。

**为什么这样设：** 日均3件防止小基数制造高倍数；销量2倍、排名减半要求变化够明显。从零起量另设30件和类目25%的规模线；2天占60%排除尖峰，5天达1.5倍看持续性，±15%容许正常走平波动，周增15%确认还在涨；降价15%提醒关注价格影响。

对应代码：[销量和排名门槛](radar/detect/rules.py#L181) · [持续性](radar/series.py#L272) · [窗口选择、从零起量和按上架天数分开](radar/analyze.py#L142)。

### 潜力和上升中有什么区别

潜力两条路满足一条：**① 下表的增长条件**；**② 上架不到90天、近1～2周就达到了上面突然爆火的门槛**（排名升一倍、日均至少2倍且至少3件、稳在高位或还在上涨；或从零起量到日均至少30件的新品爆发）。第②条不要求上架满30天、不看月趋势（新品还没有完整月份），评论少于300条、没有回落照样要满足；卡片上写“新品起量快（稳在高位 / 仍在上涨）”或“新品爆发”，和突然爆火一样写前后日均和BSR。

两类都拿旧28天正常在售日均作比较：**近28天和最近7个非大促日的日均，都要达到要求倍数**。最近7个非大促日最多回看14日；旧期未知或为零，不能靠无限倍数通过。

| 看什么 | 潜力产品 | 上升中 |
|---|---|---|
| 上架时间、评论数 | 上架30～90天；已知评论少于300条，未知不直接否决 | 不限 |
| 近28天日均 | 至少2件 | 至少3件 |
| 两段销量倍数 | 除以上涨的大盘倍数后，都至少1.2倍 | 除以上涨的大盘倍数后，都至少1.3倍 |
| 月趋势 | 近3个已结束月中，上架月之后至少有2个有效月时，平均月增长率须至少15%；不足只标“尚未验证” | 不要求 |
| 其他限制 | 不能是已识别的老品换链接 | 只给未归爆火、潜力的观察或热销商品加标签 |

**为什么这样设：** 30天先积累数据（更新的走第②条），90天和300条评论限制成熟度；潜力用2件、1.2倍尽早发现机会，上升中不限年龄，所以用3件、1.3倍提高要求。月增15%看跨月延续，最近一周也要达标，避免只靠旧涨幅入榜。

例如，近28天增长50%，但最近一周只剩旧期的1.05倍，两类都不成立。爆火、潜力先按月增量排序，同额再分别看爆发强度、增长幅度；增量怎么算见第9节。

对应代码：[潜力条件](radar/detect/rules.py#L332) · [第②条](radar/detect/rules.py#L312) · [上升中和最近一周复核](radar/analyze.py#L142) · [排序](radar/analyze.py#L880)。

## 4 什么算持续热销

“持续热销”看的是**卖得有规模、比较稳定**，不要求最近还在涨。

先定类目销量门槛：合并销售额、销量头部名单，同一父体只算一次，再取月销量第20名的销量。不足20个就取末位，无样本不设门槛。这只是采集样本的门槛，不能说成每个历史月都在全市场前20。

以下四项要同时满足：

1. 近4个已结束自然月，至少3个月达到类目门槛；每个算达标的月份，还须销量至少150件，或者销售额至少2万美元。
2. 近6个日历月已知月销量的CV不超过0.35。CV=标准差÷均值，越小越稳定；缺月留空，不强求6个月都有值。
3. 近3个月能算趋势时，平均每月下降不能超过15%（月趋势不低于−15%）；算不出趋势不单独否决。
4. 近28天日均，至少达到上述6个月已知月份平均日均的70%。

**为什么这样设：** 类目前20提供相对规模，150件或2万美元避免小类目门槛过低；4个月有3个月达标，允许偶发波动。CV 0.35、月趋势−15%、近期70%让正常起伏能通过，但挡住明显衰退。

按6个月已知月销量的平均值从高到低排序。近期回落可以保留热销并提示，但不能继续算增长。

**没查日数据，也可以补判热销**，但必须与已追踪商品不同父体，且连续6个月都在该类销售额或销量前50。还要有报告期有效的近30天销量，用销量÷30估近期日均，再按大促、修订处理和上面四项判断。

补判商品不画日走势图、不判日度回落，也不算进日数据追踪数；异常分达线就归异常，可以另标“长期头部”。

**为什么这样设：** 连续6个月头部记录弥补没有日数据的不足；再查近30天，避免只凭过去成绩入榜。

对应代码：[类目门槛](radar/analyze.py#L107) · [热销条件](radar/detect/rules.py#L251) · [月度补判](radar/analyze.py#L778)。

## 5 回落、断货恢复和老品换链接

### 什么情况算近期回落

下面任意一条成立，就不再算爆火、潜力、上升中；持续热销可以保留并提示。比较时跳过大促日，缺数据不补零。

- 最近3天日均，低于近28天最高连续3天日均的75%，**而且**低于紧挨着的前3天日均的90%。两项要一起满足。
- 最近7天销量中位数，低于前7天中位数的85%。
- 近7天最高销量之后，连续至少3个有效观察日没回升，最后一天不超过峰值的70%。

**为什么这样设：** 75%和90%一起用，确认明显低于高点且还在往下走；周中位数85%看整周走弱，连续3次且降到70%补抓快速下滑，减少单日波动误判。

对应代码：[三种回落判断](radar/detect/rules.py#L115)。

### 怎么分清增长和恢复供货

只有下面三项同时成立，才按“断货恢复”处理，不算增长：

1. 爆火所用旧期排除大促后，明确零销量或BSR达到断货线的日子，至少7天，而且至少占这段天数的25%。
2. 旧期再往前90天，至少有14个非零销售日。
3. 这些更早销售日的日均，至少达到近期日均的一半。

缺数据不能当断货证据。**为什么这样设：** 一周、四分之一要求断货确实压低了旧期水平；90天内14个销售日且卖到近期一半，避免凭零星历史就认定只是恢复。

对应代码：[断货恢复](radar/detect/rules.py#L160)。

### 什么算老品换链接

有些链接上架不久，却继承了老链接的评论或销售基础，不能直接当真新品。先要求上架不超过180天，再算“累计评论÷本ASIN已观测累计日销量”：

- 比例至少50%，符合。
- 比例至少15%时，还要有下面任意一条证据，才符合。

1. **开卖首周就卖得多**：日均至少5件，而且至少达到近7天日均的一半。
2. **后来突然上量**：先取“5件、近7天日均一半”中的较高值。首次日销达到它后，从这天起一周的日均也要达到；紧挨着的前一周日均，不超过后一周的10%。
3. **评论可能继承而来**：有效抽查的近60天评论量，不到按累计评论和上架天数折算应有量的一半。

识别后，不算潜力或从零新品爆发，不用继承评论给留评率、新品评论比加分；如果自身满足稳在高位、仍在上涨或上升中，仍可入选。旧期涉及开卖首周只作标注，增量是否算0另见第9节。

**为什么这样设：** 50%要求评论存量明显偏高，15%还要补充起量或继承证据；5件、近期一半和前后10%的要求，减少把正常投广告起量的新品误判为换链接。

对应代码：[换链接识别](radar/detect/rules.py#L37) · [继承评论检查](radar/detect/fakehot.py#L284)。

## 6 异常信号怎么计分

异常分用来决定**先核查谁**，不是刷单概率。至少3分进异常榜，至少5分列为较高风险；分数高的在前，同分时近28天日均高的在前。评分偏低仍优先归低评分。空榜不代表没有异常，也不能为了填榜降低要求。

三种评论比率看的时间不同：

- **留评率**：名单统计期的新增评论÷同期销量。
- **新品评论比**：累计评论÷完整累计销量。
- **评论增速**：两次观察之间新增评论÷同期销量。

它们都可能在说“评论相对销量太多”，重叠时要少加分，不能把同一件事重复当证据。

| 信号（点击看代码） | 什么时候加分 | 分值 |
|---|---|---|
| [留评率偏高](radar/detect/fakehot.py#L133) | 扣Vine后新增至少10条；留评率至少6%，而且至少是类目中位数3倍 | +2 |
| [新品评论比](radar/detect/fakehot.py#L168) | 上架不超过90天、总评论至少20条；扣Vine后累计评论÷完整累计销量至少10% | +2；留评率已加分则只+1 |
| [评论增速偏高](radar/detect/fakehot.py#L193) | 扣Vine后新增至少10条；同期完整销量全零，或该比率至少15%且至少是类目留评率中位数3倍 | +2；前两项任一已加分则只+1 |
| [评分跳升](radar/detect/fakehot.py#L231) | 比45天内前次有效观察提高至少0.2分，总评论至少50条 | +1 |
| [销量脉冲](radar/detect/fakehot.py#L240) | 近30天有1～3天冲高，起点至少为前28天销量中位数3倍且至少6件/天；之后间隔至少3天、最多看7天，已有销量的日均回到基线1.3倍以下；不在大促日 | +1 |
| [评论集中](radar/detect/fakehot.py#L264) | 样本至少10条，评论最多的3天合计占至少30%，且条数超过同样样本量、跨度下随机分布的99%参考上限 | +2 |
| [非验证购买多](radar/detect/fakehot.py#L270) | 至少10条评论有明确验证购买标记，其中未验证购买至少占50% | +1 |

**为什么这样设：** 较强信号2分、辅助信号1分，3分和5分区分核查优先级。6%和类目3倍兼顾绝对、相对偏高；10%和15%要求差距明显，10条、20条、50条和0.2分减少少量评论误触发；未验证购买过半也只加1分，避免只凭这一条下结论。

“评论最多的3天”不要求连续；占比和99%随机参考上限要同时达到，减少小样本误报。99%不是说有99%概率刷评。

对应代码：[总分和风险等级](radar/detect/fakehot.py#L332) · [随机参考上限](radar/detect/fakehot.py#L302)。

### 哪些情况不能拿来加分

- 评论、销量必须属于同一父体范围，不能再除以变体数。名单新增评论超过“总评论×1.05+5”，说明可能混了统计范围，不计留评率；确认评论继承或换链接时，不计对应留评率、新品评论比。
- 算评论增速，旧评论数优先取此前45天最高值，没有才用前次有效观察。例如100→80→95，不是新增15条。确认父体、变体合并时，不计相关评论增速。
- 两次观察之间每天销量都要完整、非负、有效，缺一天就不算比率；“销量全零”要有明确记录。新品累计销量要覆盖上架月至截止月已有销量，月数据不齐再查上架日起完整日数据，仍不齐就不计，未来月份忽略。

对应代码：[历史评论基准](radar/detect/fakehot.py#L45) · [完整累计销量](radar/detect/fakehot.py#L85) · [观察间完整销量](radar/series.py#L319)。

### Vine评论怎么扣

Vine是亚马逊官方免费试用评价，不能直接当异常。有有效核查、能算Vine比例时，按样本估计应扣数量；没有可用比例、且上架不超过90天时，对累计前30条作可能Vine的保守扣减。**90天和30条是项目参数，不是平台规定，也不是认定该商品一定有30条Vine。**

三种评论比率各按自己的时间段扣，不能每次对新增评论重复减30条。扣前达线、扣后没达线的新品，仍要保留待核查资格。Vine样本占比至少30%、变体合并、大促脉冲只加解释标签，不加异常分。

**为什么这样设：** 90天内预留30条，给正常新品测评留余地，避免只因评论多就误判；有核查后再用实际比例。

对应代码：[Vine扣减](radar/detect/fakehot.py#L124) · [观察间扣减不重复](radar/detect/fakehot.py#L206) · [样本Vine数量](radar/detect/fakehot.py#L294)。

## 7 评论怎么核查

每期最多15次补查，评论查询、父体和变体详情查询共用。其中5次留给未上榜、异常分至少2分的候选，用不完再分给其他核查。一次调用不等于一条评论，也不保证把一个商品的所有补查做完。

评论数比前次上涨至少30%、又没有有效详情核查时，先查父体和变体。其他评论查询按顺序安排：可疑上榜商品 → 报告点名及开发参考候选 → 未上榜且至少2分 → 其他爆火、潜力 → 可能因Vine扣减而没达线的新品。同级结合异常分、增长强度、销售额排序，仍要保证预留名额；没查到不能算核查通过。

对应代码：[核查名额和顺序](radar/verify.py#L83)。

### 抽到的评论能不能用

抽到多少条、总共有多少条，分开记录，不能把一部分当成全部。

- 查询和返回结果过滤用同一截止日，取此前约60天最新评论。只抽到一部分时，集中度按“最早样本日至截止日”算，跨度至少7天；确认取全才按60天。过滤后全空，不能记成一次新的有效核查。
- 验证购买标记要明确为是或否，缺字段不能算未验证；至少10条有明确标记才算比例。Vine比例要求所有抽样评论都有标记。
- 零样本、但总量非零或未知，不能证明没评论。旧核查没记录标记样本数，就不能沿用其比例；有依据的条数、集中度可以保留。

对应代码：[评论样本统计](radar/verify.py#L35) · [样本能否复用](radar/evidence.py#L46)。

### 核查结果能用多久

取得核查后0～13天内可用，满14天失效。若记录了评论样本截止日，该日距“判定日、商品数据日”中较晚者，也要在0～13天内。“何时查到”和“评论查到哪一天”要分开存。

核查还要绑定当时的父体、变体结构。父体换了，原评论核查就失效；变体数量变化至少2个，**而且**达到旧数量30%，也失效。例如原来10个变体，至少变化3个才达线。

详情要保留变化前后结构，更新父体前保存旧记录；同一天评分变了也要保存，缺字段不能覆盖已有有效值。重新判断过去一期时，只能用当时已取得的核查和商品结构，不能拿后来查到的结果给过去加分或豁免。

**为什么这样设：** 15次里留5次，避免未上榜候选长期没人查；14天避免旧证据一直沿用；60天、至少7天让集中度比较有统一范围；变体变化同时达到2个和30%才失效，过滤小调整。

对应代码：[14天有效期](radar/evidence.py#L25) · [父体和变体变化](radar/evidence.py#L34) · [历史回看](radar/analyze.py#L594)。

## 8 外观和材质怎么看

### 先分清和谁比较

标题比较“增长商品”和“全部月度头部商品”，至少要有3个增长、20个头部。主图取势头前50个增长，对照最多40个不属于增长的持续热销商品，另补开发方向需要的样本。标题、主图的来源分开说明，颜色有主图时优先看图。

每项外观特征，至少要有2个增长商品、2个已知品牌支持。品牌未知的商品仍算在商品总数里，但不能拿不同ASIN充当不同品牌。

| 怎么写 | 要满足什么 | 能说明什么 |
|---|---|---|
| 更多 | 至少10%的增长商品标题有该特征，且修正后占比至少为头部1.3倍；或者主图中增长侧比对照高至少10个百分点 | 在对应样本里更突出 |
| 常见 | 没进“更多”，增长侧占比至少30% | 多个增长商品都有，不表示比对照多 |
| 也有 | 没进前两档，增长侧占比至少10% | 有一些支持，比“常见”弱 |

“高10个百分点”比如40%减30%。算标题占比倍数前，两组计数各加0.5、样本数各加1，避免头部一个都没有时，倍数变成无限大。

有效标题说更多、有效主图却说更少，或反过来，这项特征三档都不列。“更多”先按占比差排序，标题和主图共同支持的适当前置；每个维度最多6个更多、3个常见、6个也有。

其他结构化共性要有至少2个商品、增长占比至少20%、修正倍数至少1.5，最多10条。关键词通常至少3个商品支持；增长样本少于20时，改用“2、样本量15%向上取整”中的较高值；修正倍数至少2，最多15条。这里只能说经常一起出现，不能说这些特征导致销量增长。

**为什么这样设：** 2个商品、2个品牌减少单个卖家重复铺款的影响；10%加1.3倍、或高10个百分点，同时要求有覆盖、有差距。30%和10%区分支持强弱；50个增长、40个对照及展示上限控制成本、阅读量，不保证统计结论一定可靠。

对应代码：[标题特征比较](radar/detect/design.py#L198) · [主图比较](radar/vision.py#L180) · [两种结果合并](radar/detect/traits.py#L181) · [其他共性和关键词](radar/detect/traits.py#L122)。

### 主材质单独看

每个商品只取一个主材质，优先顺序是：**商品Material材质属性 → 标题明确写的材质 → 主图识别 → 标题笼统写的木质**。有木纹不等于实木，没有属性也不等于没有这种材质。

增长商品、持续热销分别统计材质，未知材质也保留在分母里，不直接套用外观“更多”的说法。每期材质属性最多查30次，注明来源，没查不能说已核实。

对应代码：[材质取值顺序](radar/materials.py#L68) · [材质分组统计](radar/materials.py#L106)。

## 9 开发方向、增量和成本

### 哪些类目能形成开发方向

同类目至少有2个增长商品、2个已知品牌、月增量为正，才形成候选方向（只展示有增长的品类；增长商品的增量都按0算或没多卖的不算）。按月增量总额从高到低排序，同额依次看品牌数、增长商品数、爆火数、势头。报告按配置数量展示，0表示全部；本期要点和钉钉放月增量合计占80%的那几个，个数每期不同。全部子类目一览只列有增长的，没有增长的只写个数。

没有共同特征和明确材质时，写清原因，不能硬凑画像；增量大但缺画像的，另作提示。

对应代码：[方向筛选和排序](radar/detect/directions.py#L101) · [画像与缺失原因](radar/detect/directions.py#L150)。

### 怎么和同类目头部比较

对照取该类月销量前30，排除增长商品和它们的同父体商品。至少有10个已知头部品牌才比较“谁更多”；不足时只列共同特征。其中至少10个品牌已识别主图，两边都用标题和主图，否则都只用标题。

为防一个品牌铺很多相似款影响结果，先算各品牌内部有这个特征的比例，再给每个品牌同样权重。例如A品牌5/10个有、B品牌1/1个有，品牌平均占比就是(50%+100%)/2=75%。

- **比头部多**：至少2个品牌支持，增长侧品牌平均占比比头部高至少20个百分点，而且至少是头部1.5倍。
- **基本款**：至少2个品牌支持，增长侧品牌平均占比至少50%，且没进“更多”；对照不足时称共同特征。每个维度每档最多3项。
- **主材质**：一个品牌只要有任一增长商品用这种材质，就算支持；至少半数已知品牌、而且至少2个品牌支持才列，不直接说比头部有优势。
- **价格和参考商品**：列有效售价的最低～最高值，至少3个有效价格才给中位数。参考最多2个，异常分必须为0、来自不同已知品牌；不足就少列，0分也不代表已证实安全。

**为什么这样设：** 至少10个头部品牌减少单品牌偏差；高20个百分点且达1.5倍，避免把品类普遍特征当机会。50%找多数品牌具备的基本款，双品牌参考减少重复；摘要5个、每档3项方便执行，完整证据仍保留。

对应代码：[品牌平均占比](radar/detect/directions.py#L80) · [头部对照](radar/detect/directions.py#L115) · [特征分档](radar/detect/directions.py#L150) · [参考商品](radar/detect/directions.py#L129)。

### 月销售额和月增量怎么算

估算月销售额 = 最近28天日均×商品售价×30。

估算月增量 =（最近28天日均−再之前28天正常在售日均）×同一售价×30。

两项都按相同规则处理大促和销量修订。旧期水平未知，写“无法估算”，不计合计；能算出的负增量照留。下面这些情况，增量按0算并写清原因：

1. 已识别老品换链接，旧28天没有在卖基准，或在卖不足14天；如果旧期本身未知，仍优先写无法估算。
2. 从零起量但属于“老链接重新起量”；或者上架超过180天、旧28天在卖不足14天。
3. 只是回到以前卖到过的水平：在旧期开始前56天内，找有效在卖至少14天的连续28天最高日均；近期没超过它。爆火用选中的7天或14天日均核对，其余增长用28天日均。
4. 没有售价，算不出金额。

**增量算0只影响增量金额和排序，不自动取消增长标签**，所以增长商品也可能没有正月增量。

**为什么这样设：** 旧28天至少14天在卖，才有较充分的老链接比较依据；回看56天防止恢复销量排到开发方向前面；乘30是统一成月度量级便于比较，不是自然月实际收入。

对应代码：[月销售额](radar/analyze.py#L34) · [月增量](radar/analyze.py#L83) · [增量算0的原因](radar/analyze.py#L38) · [历史高位](radar/analyze.py#L68)。

### 包装和FBA费用怎么看

这里的FBA指亚马逊配送费估算。必须用包装尺寸、重量，不能拿组装后的尺寸代替。英寸长×宽×高÷1,728得到立方英尺，再×0.0283168得到立方米；重量统一用磅。

体积、重量、费用分别用有数据的商品取中位数，所以样本数可能不同。FBA占售价的比例先逐商品算，再取中位数。销量、金额、费用都要注明估算；算利润还要加上采购、头程、佣金、仓储、广告、退货等成本。

对应代码：[包装单位换算](radar/shipping.py#L32) · [费用汇总](radar/shipping.py#L81)。

### 开发方向一览上的市场数字

一览每行一个子类目：月增量、价格带、新品占比、头部评论、比头部多的特征；点一行弹出价格分布、完整画像和这个子类目的增长商品卡片。市场数字只读**本期翻到的全市场名单**（近30天销量≥300件或销售额≥$4万的商品，读的时候再按范围过滤一次），不花调用，也不参与任何判定。本期没翻全市场名单时这几列写“—”，不拿旧名单说现在的市场。

- **主力价格带**：按近30天销售额加权的售价P25～P75，一半的销售额落在这个区间；竖线是P50。便宜货多但卖得少，不会把价格带拉低。
- **价格分布**（小窗里）：各价格段（$25、35、50、70、100、140、200、280、400、560、800，约每档×1.4）占名单销售额的比例；下面的点是这个子类目增长商品的售价，颜色区分突然爆火 / 潜力 / 上升中。
- **新品占比**：上架≤180天（`report.market.new_days`）的商品占这个子类目名单销售额的比例，看新链接能不能分到钱。上架日期是卖家精灵给的代表子体的。
- **头部评论**：名单里销售额前20名（`head_n`）的评论数中位数，新品大致要追的评论量。
- **品牌集中度**（小窗里“前5品牌”）：销售额前5个已知品牌（`top_brands`）占名单销售额的比例；缺品牌的商品不算任何品牌。

名单里的销量、销售额是父体合计，所以这里只用比例和中位数，不写绝对金额。

对应代码：[市场数字](radar/detect/market.py#L45) · [一览和小窗](radar/report/render.py#L1092)。

## 10 和上期比较，什么时候发布

### 和上期相比，变化怎么写

- **依旧爆火**：上期、本期主要分类都是爆火。
- **新进入**：上期不在这个板块，本期进入；从别的板块转来要写清楚。
- **不再爆火**：上期爆火，本期还在追踪，但变成观察或低评分。转成潜力、热销、异常的，列在对应变化里；本期没追踪，不能说成回落。
- **月度补判**：以前没覆盖，这期靠历史名单判出热销，要单列补判，不能说刚开始热销。回看未追踪商品的上期结果要注明；上期提示待修订时，要复核全部上期增长商品。

对应代码：[两期变化](radar/detect/diff.py#L16) · [上期结果复核](radar/detect/diff.py#L42) · [上期回看](radar/pipeline.py#L644)。

### 哪些问题只提醒，不直接改分类

- 增长商品变体数比旧记录增加至少30%，而且至少增加2个。
- 近30天名单销量、日销量合计都至少60件，却相差至少2倍。
- 最近28天至少缺7天日数据。

另外，近10天若至少有40个合格样本、过去排名中位数不高于30万，其中至少10%排名改善到原来的1/1.8，而且连续至少2天出现这种情况，就提示销量可能还没修订。以上提示不能代替各板块自己的判断。

对应代码：[商品数据提醒](radar/analyze.py#L564) · [大范围BSR改善](radar/detect/events.py#L50)。

### 预算不够或数据失败时怎么办

运行间隔14天，每月最多2,000次调用，剩余额度按本月剩余期数均分，单期最多2,500次。评论和详情核查15次、材质查询30次、月度名单补齐50次都是上限，都要算进总预算。

按北京时间自然月记账；密钥如果还给其他服务用，要给它们留额度。核心采集失败、刷新不足、整批数据过期时，不发布新一期，保留旧报告和采集进度，供下次重试。

**为什么这样设：** 14天、每月2,000次平衡时效、覆盖和成本；15次、30次、50次避免补查挤占日数据名额；2,500是单期保护上限，仍不能超出月度剩余额度。

对应代码：[运行间隔](radar/pipeline.py#L98) · [预算分配](radar/pipeline.py#L210) · [发布前检查](radar/pipeline.py#L334) · [失败保留进度](radar/pipeline.py#L44)。

## 11 报告里列哪些商品

判定不变，只是**列出时挑一遍**：位置有限，多放不同的、有特色的商品。

- **特色**：主图识别和标题里看得出的、这个品类基本结构以外的设计——工艺（凹槽竖纹、藤编、谷仓门、玻璃门、锥形腿……）、开放格 / 立式 / 窄小 / 落地 / 模块以外的造型（圆形、拱形、L形、悬浮……）、抽屉以外看得见的功能（灯带、插座、升降台面、电子壁炉、轮子……）、藤编 / 大理石纹 / 岩板 / 亚克力。标题里的免安装、防倾倒、防水这类说明不算。
- **简单款**：主图识别过，主图和标题都没有任何特色，数据达标也不列（例：开放格收纳柜、金属平台床架、普通三层边几）。双色拼接、高光烤漆、做旧、金色拉手只是表面处理，只有这些的也算简单款。没识别主图的不判，照常列出。
- **各子类目的基本结构**：一个子类目里主图识别过的商品（至少10个）有一半以上都有的造型或功能，算这个品类本来的样子，不算特色。例如衣帽架的挂钩和单柱底座、梳妆台的镜子和灯、电动升降桌的升降、床头柜的插座。所以只有单柱和挂钩的铁艺衣帽架也是简单款。工艺（凹槽竖纹、玻璃门……）和特殊材质再常见也算设计，不按子类目扣；特殊材质以主图为准，标题里的 stone、marble 常是底座配重或颜色名，不算。
- **相近款**：同一个子类目里，和已经列出的一款“主图特征重合度、标题用词重合度的平均”至少50%，或者都带电子壁炉 / 升降台面这类决定款式的功能，只列排在前面的那款，其余记在它的卡片上。

KPI数字、卡片、图墙、钉钉消息和本期要点点名的商品都按列出的算；小窗顶部写明“判定几个、列出几个”。简单款报告里哪里都不放图和品名，只写个数：小窗、与上期对比（11-02：“新进入「突然爆火」12（简单款 2 个没列）”）、开发方向的缩略图和价格点、全部追踪商品表都一样。外观与工艺依据、开发方向的统计仍用全部增长商品：长得普通的也是真实需求。开发方向的参考商品不选简单款。

商品多的小窗顶部可以按类别、子类目筛选，按月增量、售价、上架天数、评分排序；只改显示顺序，不改判定。图墙上的迷你走势是近56天日销量，阴影是判定比的最近几天（突然爆火7或14天，其余28天），两段横线是前后两段各自的日均。

报告上每个板块只写一句话的条件，这份 README 是完整口径。

**为什么这样设：** 11-02那期突然爆火22个里有7个是开放格柜、金属床架这类简单款，增长商品里电子壁炉电视柜、升降茶几、LED储物床各出现3~5次；挑完后突然爆火列13个、增长商品列63个、持续热销列69个，图墙12个来自12个子类目。子类目基本结构这一条去掉了5个普通铁艺 / 实木衣帽架和4个只多一个插座的窄条桌，都是一眼看上去的普通款。50%是对着这期商品逐对看过定的：40%会把不同款的床、不同风格的电视柜也并到一起。

对应代码：[特色和简单款](radar/detect/showcase.py#L54) · [子类目基本结构](radar/detect/showcase.py#L85) · [相近款](radar/detect/showcase.py#L128) · [挑选顺序](radar/detect/showcase.py#L144) · [各板块列出的商品](radar/pipeline.py#L578)。

## 12 什么算蓝海产品

蓝海产品是**和某个小众兴趣爱好直接相关的家具 / 收纳**：桌游桌、拼图桌、爬宠箱和鱼缸柜、唱片机柜、手办 / 乐高展示柜、缝纫手工桌、绘画桌、音乐工作台、街机柜、台球桌、枪柜、钓竿架、雪茄柜……玩这个爱好的人才买，圈子小、做的卖家也少。2026-11-06 起只认兴趣爱好：人群 / 场景 / 商用的（蒙氏地床、卧床护理的床边桌、店铺前台、讲台、员工更衣柜、商用备餐台、美甲台）不再算。下面六条都要满足：

1. **兴趣爱好专用**：标题里写明了词表里的某一类（`config.yaml` 的 `thresholds.blue_ocean.niches`，每类一个正则，按顺序取第一类）。只认写明专门用途的说法。
2. **有需求**：在本期全市场名单里（近30天销量至少300件或销售额至少4万美元），在监控范围内、不是小件。
3. **圈子小**：这一类在全市场名单里够门槛的商品（同一父体算一个）不超过50个，多了就是大众品类。
4. **评分达标**（和各板块一样）。本期拉到了日数据的，还要不是异常信号、名单和日数据对得上。
5. **不是太小、结构太简单的**：圈子再小，这种品也没有开发价值。**太小** = 包装不到30磅，而且标题和主图都没有升降、翻转、折叠、翻板、暗格这类机构；**结构太简单** = 书架 / 置物架类（标题是书架、玩具架、展示架，或主图是开放格、书架、绘本架），包装不到50磅、不是超大件（三边在59×33×33英寸以内），没有柜门也没有上面这些机构——书架下面带个抽屉也还是书架。没有包装数据的判断不了，不算。
6. **近期新上架、月售够**：上架不超过365天（`thresholds.blue_ocean.max_age_days`；2026-11-06 用户定，原来和潜力产品一样是90天，11-02 现有的21个爱好类商品一个也不剩），近30天销量至少50件。只卡候选，第3条的个数照样算老款——老款也是这一类的竞品。上架日期不知道的判断不了，不算。

只用本期翻到的全市场名单，不花调用；本期没翻成就不判，不拿旧名单说现在的市场。符合的商品进追踪池拉日数据（最多40个，按近30天销售额），卡片上才有走势图；没拉到的照样列出，卡片写明“只有名单数据”。商品照样留在自己的板块里，同一类排在一起；小窗顶部列出每一类全市场有几个（老款也算）、其中符合几个、合计月销售额、几个品牌，可以按类筛选。列出时和别的板块一样去掉简单款、合并相近款（第11节）。

**为什么这样设：**

- 词表16类（`thresholds.blue_ocean.niches`）：桌游拼图、爬宠水族、黑胶影音收藏、手办模型收藏、缝纫手工、绘画设计、乐器音乐、电玩街机、台球游戏室、狩猎射击、垂钓、运动健身骑行、园艺植物、雪茄酒类收藏、3D打印摄影、漫画阅读收藏。只认写明专门用途的说法：drum table（鼓形是造型）、普通折叠牌桌、电竞桌、写着 Podium 的电脑推车、车库工具柜、coffee bar 都不算。
- 圈子小用个数卡：标题写gaming的有114个、standing desk的194个、makeup vanity / vanity desk的142个，都是大众品类，加进词表也不会算蓝海。
- 太小、结构太简单要两条一起看：只按重量切不行，42磅的漫画书架和带枪支暗格的床头柜（38～46磅）、缝纫桌（45～49磅）一样重；只按结构切也不行，拼图桌结构也简单，但它不小。
- 11-02全市场名单（现在监控的家具、办公家具子类目）里兴趣爱好专用的只有21个：黑胶影音16（唱片机柜、CD / DVD塔架，多在边几、影音架、书架里）、缝纫手工2、狩猎射击2（带枪支暗格的床头柜）、手办模型1，都上架超过90天，所以这期一个也没进候选。桌游桌、爬宠箱、鱼缸柜、台球桌、乐器、钓鱼、园艺这些多在家具以外的根类目（宠物用品、玩具、运动户外、乐器、手工），要看到得另加子类目（每期多花调用、要先查子类目ID）。

## 运行与部署

### 先在本地试用

安装Python 3.11，在仓库目录运行：

```powershell
python -m pip install -r requirements.txt
python -m radar demo
```

打开`out/demo/report.html`看演示，不消耗接口调用。要查真实数据，复制 [.env.example](.env.example) 为`.env`（已有就直接编辑），填好密钥后运行`python -m radar run`。本地`site/`和GitHub线上历史分别保存，不会自动共用。

| 密钥 | 怎么填 |
|---|---|
| `SELLERSPRITE_SECRET_KEY` | 查真实数据必填，取自[卖家精灵开放平台](https://open.sellersprite.com) |
| `REPORT_KEY` | 加密必填，用`python -m radar keygen`生成，一定要备份 |
| `DINGTALK_WEBHOOK`、`DINGTALK_SECRET` | 推送时填钉钉群加签机器人的Webhook地址、SEC开头密钥 |
| `DEEPSEEK_API_KEY` | 可选，取自[DeepSeek](https://platform.deepseek.com)，用于本期要点的开发建议、主图识别；不填则开发建议按数据挑选，只用非视觉证据 |

### 放到GitHub自动运行

1. Fork仓库并启用Actions，在 **Settings → Secrets and variables → Actions → Secrets** 填入上面的密钥。
2. 在 **Settings → Pages → Build and deployment** 把Source设为 **GitHub Actions**。
3. 在 **Actions → 家具爆品雷达 → Run workflow** 选`mode: run`。`force`忽略14天间隔，`notify`控制是否推送，`budget`设置本次调用上限。开启推送后，从钉钉卡片打开报告。

Windows也可安装GitHub CLI，运行`gh auth login`后，再运行`powershell -ExecutionPolicy Bypass -File scripts\setup_secrets.ps1`配置密钥。脚本读取`.env`，缺少`REPORT_KEY`时会生成并保存。

要推送多个群，每群新增一个Secret，从`DINGTALK_ROBOT_1`到`5`，值为`Webhook地址,SEC密钥`，中间用英文逗号；超过5个群要修改工作流。

### 常用操作

| 想做什么 | 命令或入口 |
|---|---|
| 忽略间隔，查真实数据并推送；会消耗调用 | `python -m radar run --force --notify` |
| 用已保存数据重新生成，不重新采集 | `python -m radar rerender`；线上选`mode: rerender` |
| 补发最近一期通知 | `python -m radar notify` |
| 检查机器人和链接 | `python -m radar test-dingtalk --with-key` |
| 查看本地状态、全部命令 | `python -m radar status`、`python -m radar --help` |
| 验证代码，不调用真实服务 | 安装`requirements-dev.txt`后运行`python -m pytest -q` |

配置分工：`scope/discovery/pool`管范围和采集，`thresholds`管判断，`schedule/budget`管周期和预算，`llm`管模型，`report/notify`管报告和通知。报告保留最近60期，模型费用另算。

## 出问题时怎么查

- **没出新报告**：查Actions日志或钉钉告警；重试会复用有效进度、重查过期数据。已有新数据但还没发布时，先完成正常运行，不能直接`rerender`旧一期。
- **商品没入选**：依次查范围、销量门槛、日数据、评分、数据日期、旧期数据和排除原因，分清是“没覆盖到”还是“查了但没达标”。
- **通知或链接打不开**：先看同一个机器人的Webhook、SEC是否配对，再查网络、链接密钥。换域名用`REPORT_BASE_URL`，线上填Actions Variables，本地填`.env`。
- **数据放哪里**：源码在`main`，线上加密数据和报告在`site`分支；公开站点不能含`data/`。报告链接`#k=`后是该期解密密钥，分享完整链接，就等于允许对方查看该期。
- **哪些要备份、不能提交**：备份`REPORT_KEY`，丢了无法恢复历史。`.env`、本地`site/`、`out/`、解密明文不能提交源码分支。密文触发推送保护时，可用`python -m radar reseal`重新加密。
